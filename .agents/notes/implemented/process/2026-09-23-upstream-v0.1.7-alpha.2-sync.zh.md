# Agent Note: 上游 v0.1.7-alpha.2 同步

Status: implemented

[English](2026-09-23-upstream-v0.1.7-alpha.2-sync.md) | 中文

## 问题

本次同步把 fork 的跟踪点从上游的 `dsh-v0.1.7-alpha.1` 标签（即本次合并的基点）推进到 `dsh-v0.1.7-alpha.2` 发布。上游前进 162 个提交、涉及 869 个文件（+21355/−11052），fork 自带 598 个，合并有 106 个路径冲突。

本版有两处改动撞上了 fork 自己写下的内容。上游退役了 `workspace:^` 依赖区间：DSH 包改用 `workspace:*`，`vendor/` 与 `native/` 改用 `workspace:~`，而 `check-workspace-constraints` 现在对它读到的每一份清单都推导这一期望，包括上游并不发布的 47 份清单——其中 45 份带的正是被退役的区间。上游还重写了 sensevoice 的 worker 规格：fork 侧那段本地同步只为让被它删掉的调用计数轮询不产生竞态而存在。

## 决定

- **fork 的清单采用上游的发布区间。** 合并后的树里没有任何清单声明 `workspace:^`；每个 DSH 依赖读作 `workspace:*`，每个 `vendor/` 或 `native/` 依赖读作 `workspace:~`，正是 `check-workspace-constraints` 接受的那一对。上游自己的清单是转换后到来的，因此把 fork 的 45 份留在被退役的区间上，会让门在上游根本不读的文件上失败。
- **上游那两份带重复键的清单保持原样。** `packages/llm/llm-retry/package.json` 在 `dependencies` 内重复了 `@deepseek-ai/dsh-session-projection`，`packages/client/ui-sidebar-documentpreview/package.json` 同样重复了 `@deepseek-ai/dsh-office-to-pdf`，两处都出现在两个父提交与基点提交中，且各自重复的两个值相同。JSON 的后写覆盖使生效依赖不变，而在合并中改写一份上游写的清单会把 fork 内容放到上游拥有的文件上，并在下次同步时再次冲突。
- **三份 fork 清单的重复依赖段落被合并收拢，没有条目随之丢失。** `packages/experimental/webhook` 与 `packages/session-query/session-query` 各有两个顶层 `dependencies` 对象，生效的是后一个；合并后的清单只有一个对象，装着 fork 全部 3 条与 2 条条目。`packages/api/remotes` 在两个父提交里都重复了五个 `devDependencies` 键，合并后的清单里没有一个键出现两次，同时保留 fork 全部 34 条条目与上游新增的那一条。每对重复键只持有一个值，因此这次收拢就是该文件自身的生效内容，而不是在两侧之间做选择。
- **client 装配保留 `sessionFeedbackRemote`。** 自动合并丢掉了 `packages/api/remotes/src/client/index.ts` 中 `@deepseek-ai/dsh-command-feedback/remote` 的导入与它在挂载列表里的条目，使该命名空间未被挂载，而构建期不会有任何东西失败。两者都已恢复，该列表中 fork 的五个 Remote 贡献——`pluginMarketRemote`、`pluginRegistryProbeRemote`、`messageFeedbackRemote`、`sessionFeedbackRemote` 与 `fileUploadsRemote`——与上游自己的贡献并排挂载。
- **sensevoice 的 worker 规格采用上游的重写，而非 fork 的同步。** 上游的用例去掉调用计数轮询、改为等待 `handle.done`，并把主体包进 `try`/`finally`；fork 新增的那段同步只为让该轮询存活，把它留在重写旁边只会为一道不再运行的操作留下守卫。
- **`timeout-guard` 在 fork 的名字下套用上游最新的源码。** 上游的 `packages/guard/timeout-policy` 本版再次改动；合并后的 `packages/guard/timeout-guard/src/index.ts` 与上游文件只差模块文档注释与注册的 `name`，合计 13 行，因此上游的行为落地，而 fork 改名退役掉的包名不会复活。
- **并集冲突保留两父提交的新增。** `apps/desktop-host/src/index.ts`（两侧各加一个 `node:` 导入：`fileURLToPath`、`inspect`）、`packages/api/gateway/src/index.ts`（上游的 `assertResolvedConfig`/`isPlainObject` 值导入与 fork 的 `dsh-cmdline` 纯类型导入并列）、`packages/extensions/tool-cordis/src/api-catalog.ts`（两份目录的条目）与 `apps/desktop/tests/main-startup.spec.ts`（两套规格的导入与用例）都解析为并集而非择一侧，因为每处新增都被合并后仍在的代码读取。
- **版本族在合并提交内对齐。** fork 的 350 份 `packages/` 清单、4 份 `apps/` 清单与根清单移到 `0.1.7-alpha.2`，与上游自己的清单并列；fork 唯一的版本镜像 `SIDEBAR_SERVICE_VERSION`（已随 PR #677 删除的 better-sidebar 包的 `service.ts`）随它们一起移动。随后 `pnpm exec tsx scripts/release/verify.ts --family dsh` 解析该族：352 个成员、单一版本、发布顺序可解。`packages/bundle/web-app/package.json` 的 `js-yaml` 保持在 `"^4.2.0"`：这是第三方依赖的 registry 区间，不归发布区间规则管。
- **生成目录与双语记录在已解析的树上重新生成。** `docs/capability-seams.md`、`docs/config-catalog.md`、`docs/persistence-catalog.{md,zh.md}` 与 `docs/persistence-schema.json`，以及 preset 的 `cordis-composition-reference` 技能所生成的组合参考（该技能已在 v0.2.2-rc.2 中删除），都在冲突解析之后由各自的生成器产出；每个被改动的配对通过 `pnpm run verify-translation-pairing --write` 重录 blob 哈希。

## 后果

fork 带着完整的专利、文档、桌面、better-sidebar、synapse、self-evolve 与插件市场面发布上游的 v0.1.7-alpha.2 基线：47 份清单只存在于本树，其中 44 份在 `packages/` 下；上游唯一未被本树携带的清单是 `packages/guard/timeout-policy`——它的内容以 `timeout-guard` 之名继续存在。依赖声明现在在两棵树上读法一致，因此 fork 自己的包接入上游的发布工具链，而代价是上游每退役一个区间就要在同步时改写一次。client 装配的挂载列表是本次合并悄悄丢掉 fork 贡献的唯一位置，如今它必须携带的命名空间已被记录在案。

## 考虑过的替代方案

- **只转换 fork 专有的清单，不动上游的区间。** 不可行：上游的清单是转换后到来的，而该门一遍读完每份清单，因此部分转换会因为同一个原因在同一道门上失败。
- **趁合并开着时顺手去重上游那两份带重复键的清单。** 否决：重复键持有相同的值，改写不改变任何解析结果，却会把 fork 内容移到上游拥有的文件上，在下次同步时再次冲突，并掩盖条目究竟由哪一侧写下。
- **在采用上游 worker 规格重写的同时保留 fork 的同步。** 否决：它同步的调用计数轮询正是重写删掉的东西，保留的代码会等待规格不再产生的信号。
- **恢复上游的 `timeout-policy` 名字并退役 fork 的改名。** 否决：fork 已记录该改名，而上游的源码除名字外原样转移，取回名字会为零行为收益重开一个已定的决定。
- **在 client 装配的挂载列表上取上游那一侧。** 否决：该文件里 fork 的新增挂载的是本树发布的命名空间，且自动合并已经丢掉了其中一个；该列表按构造是两父提交的并集。

## 测试

`pnpm run test` 在合并树上跑完整单元套件：2268 个文件中的 2249 个、42291 个用例中的 42111 个通过，剩余三处失败属环境约束而非合并造成。`packages/boot/hmr/tests/watch-config.spec.ts` 是一条 10 秒的 fs-watch 截止线，单独跑 3 次失败 2 次，而在套件其它负载下通过；`packages/boot/hmr` 与 fork 父提交只差 `package.json` 的区间。`packages/subprocess/subprocess-local/tests/spawn-runner.spec.ts` 期望八个 Windows 可执行文件探测点，在 `env -u NoDefaultCurrentDirectoryInExePath` 下 35/35 通过，因为 Bash 工具的环境注入了 `NoDefaultCurrentDirectoryInExePath=1`，它使 `resolveWindowsExecutable` 跳过该用例所断言的裸当前目录根；该规格与 `runner-launch.ts` 都与两个父提交逐字节相同。`packages/util/http-proxy/tests/install.spec.ts` 的 fetch 在 1502 毫秒被正确拒绝，但它的 `dispose()` 要等待一个连接器，而本机上 `origin.test` 的解析耗时 30007 毫秒，超出 5000 毫秒预算——即上次同步记录的同一宿主约束。`pnpm run typecheck` 覆盖两个面（退出 0）；`pnpm run lint` 报 0 warning / 0 error；`pnpm run duplication` 报 0 克隆；`pnpm run build` 通过。`pnpm run hygiene` 报 19 门通过 / 0 失败 / 0 跳过，含 `constraints`；`pnpm run doc-sync` 报 44 门通过。`pnpm exec tsx scripts/release/verify.ts --family dsh` 解析 352 个成员、版本 `0.1.7-alpha.2`，持久化三道门（`verify-persistence-formats`、`verify-persistence-releases`、`verify-persistence-changes`）接受所记录的状态。覆盖本次合并触及包的定点套件跑 42 个文件、894 个用例，`apps/desktop/tests/main-startup.spec.ts` 跑 89 个，`scripts/check-workspace-constraints.spec.ts` 跑 102 个。
