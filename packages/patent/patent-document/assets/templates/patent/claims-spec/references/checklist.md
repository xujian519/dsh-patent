# 权利要求书与说明书 — 自查清单（Checklist）

> 输出 `<artifact>` / 定稿前逐项勾选。P0 必须全部通过。

## P0 — 必须通过

- [ ] 文书结构完整且顺序正确
- [ ] 案件信息表填满（发明名称、申请人、发明人、代理人/代理机构、撰写日期）
- [ ] 权利要求书至少包含 1 项独立权利要求和必要的从属权利要求
- [ ] 从属权利要求引用格式正确（"如权利要求 X 所述的……，其特征在于……"）
- [ ] 权利要求无模糊词（"大约""基本上""优选"等）
- [ ] 说明书包含技术领域、背景技术、发明内容、附图说明、具体实施方式五部分
- [ ] 发明内容明确写出要解决的技术问题、技术方案、有益效果
- [ ] 具体实施方式至少包含一个完整实施例，并引用附图标记
- [ ] 摘要不超过 300 字，含发明名称、方案要点、主要用途
- [ ] 经 `render_patent_document` 传**受控草案 `draft`** 渲染（不再接受手写 innerHTML；不要手工复制模板另存——手工路径下品牌注入、落版与段落编号声明都不会生效）
- [ ] 说明书不带多余标题：除技术领域、背景技术、发明内容、附图说明、具体实施方式五部分外，正文（含要解决的技术问题、技术方案、有益效果、实施例X）不加标题
- [ ] 说明书正文的附图标记不加括号（写作「模块1」，不是「模块（1）」），图号写作「图1」不留空格
- [ ] 附图说明列表项只写图名与描述文字，不自带「图N为」前缀与句末「；/。」（两者由渲染器生成）
- [ ] 表格仅出现在具体实施方式，每个表格有名称（渲染器自动生成「表 N · 名称」表题并连续编号），表头/数据行/单元格齐全
- [ ] 段落编号属于可选体例：提交体例需要时，模板节已声明 `data-paragraph-numbering`，编号由渲染引擎写入、从 `[0001]` 起不断号，改动段落后已重渲；不需要时说明书不出现 `[NNNN]`
- [ ] 权利要求书、摘要内不出现段落编号（摘要里出现的附图标记应加括号）
- [ ] 权利要求得到说明书支持，无修改超范围风险
- [ ] 无占位文案泄漏给用户（`________` 类占位全部替换）

## P1 — 应当通过

- [ ] 权利要求层级递进合理，保护范围由宽到窄
- [ ] 功能性限定有实施例支持
- [ ] 背景技术客观描述，不贬低他人专利
- [ ] 附图标记在说明书与附图说明中一致
- [ ] 摘要不含商业性宣传用语

## P2 — 锦上添花

- [ ] 同时产出内部审稿版与正式提交版
- [ ] 导出 PDF 后抽查权利要求项是否跨页断裂
- [ ] 提供 `.md` 源稿便于后续修订
