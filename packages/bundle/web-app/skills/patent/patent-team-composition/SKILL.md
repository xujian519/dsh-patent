# 专利团队组成

**建队需用户明确指示**（persona「作业模式 · 流程一」）：仅当用户在本轮明确要求组队、多角色并行或指定用专利团队时才建队；未获明确指示时一律走单会话意图驱动流程，不得因案件复杂、交付件多或任务量大而自行组队。获得指示后按作业场景选择角色包，**立场配对 + 中立裁判**是复审/无效/诉讼场景的核心结构。

## 前置条件

- 本会话已挂载 `patent_teams_*` 工具（`dsh-patent-teams` 插件）；仅当插件被禁用时回退单会话 + `subagent_fork` 专家互评。
- 一个 captain（主会话）同时只领导一个活跃团队；建队前确认无未收口的团队。
- 团队成员默认继承 captain 的 LLM 路由与 effort，不指定 provider/model；仅当用户明确要求异构团队（如"检索用 X 模型"）时才传 provider + model。
- 单团队成员上限 8（插件 `maxMembers` 默认 8，deployment 可调）；七个场景包均在此上限内。

## 人工确认点（captain 不得单方收口）

团队负责并行执行与互证，决策点仍由用户拍板；captain 只做组织、汇总与收口，不得代替用户决定策略。其中建队与收口两步已是执行点：本部署打开 `approveCreation` 与 `approveClosure`，`patent_teams_create` 与 `patent_teams_delete` 在改动前向审批服务取决策，未放行即调用失败并给出结果名（`rejected` / `cancelled` / `unavailable`）——这是正常拒绝，不得重试同一调用绕开用户，应把团队方案或结案陈词交给用户后再决定。

- 组队方案先确认：成员名单（角色与人数）、任务 DAG、预计轮次在 `patent_teams_create` 之前用 ask_user_question 报给用户确认；用户要求精简成员时按他的下线建队，不自行加角色。
- 阶段产出先过目：每个环节的关键产出（检索式与对比文件清单、权利要求布局与项数、说明书稿、修改方案、无效理由组合、图面与附图标记表、交付稿）在进入下一任务前汇总给用户看，用户确认后才继续；不得连跑数个任务后一次性汇报。
- 关键取舍不代决：涉及策略的取舍（检索范围与通道、最接近现有技术选取、修改与争辩路线、无效理由主备路径、诉请金额、交付模板与体例）由用户选择或明确授权；captain 与成员都不得「按惯例」自行决定。
- 收口与交付放行：`patent_workflow_run` 收口与正式文档渲染由用户放行；用户否决时不得宣告完成或交付，按反馈回退到对应任务并说明返工范围。
- 汇报节奏：每完成一轮任务向用户汇报一次（成员产出、未决问题、下一步与预计耗时），不静默长跑。
- 用户可随时介入：增删成员、改派任务、要求中间汇报，或退回单会话模式；退回时归档团队（`patent_teams_delete`）并向用户交代已完成产出与未决问题。

## 场景角色包与任务 DAG

### 场景一：立案包（5 成员）

成员：案件管理员、检索员、技术专家、撰写员、文档专员。目标：交底书从接收到"补充合格、可进入撰写"，并输出立案结论与反馈函。

| 任务 | 主题 | 负责人 | 依赖 |
|---|---|---|---|
| t1 | 交底书接收与登记：案卷目录、必要文件清单核对 | 案件管理员 | — |
| t2 | 初步检索与可专利性初判：申请类型建议、明显缺陷筛查 | 检索员 | t1 |
| t3 | 交底书质量评估：技术内容清楚度、可实施性、缺失信息清单 | 技术专家 | t2 |
| t4 | 反馈申请人补充资料：补充清单发出与跟踪 | 案件管理员 | t3 |
| t5 | 补充合格判定：补充内容是否满足撰写前条件 | 技术专家 | t4 |
| t6 | 正式文档输出：立案结论与反馈函整理（可专利性意见/公文），矫正 + 美化 | 文档专员 | t5 |
| t7 | 立案收口：`patent_workflow_run(manifestId=patent_patentability_v1)` 记录可专利性结论 + 立案结论、下一步撰写移交 | captain | t6 |

补充循环纪律：每次反馈须有明确补充清单（问题→依据→期望补充内容），判定不合格时列出剩余缺口后重入 t4，禁止模糊反馈。

### 场景二：撰写包（7 成员）

成员：检索员、撰写员、对立审查员、技术专家、申请人代理、制图员、文档专员。目标：新申请文件（权利要求书+说明书+附图与附图标记表）并以正式文书交付。

执行面分工：**captain 用 `patent_workflow_run(manifestId=patent_disclosure_v1)` 一次性执行到 `review_gate`，门前由用户放行**（本部署打开 `approveStageGates`：前台运行在审批门取用户决策，放行即继续，拒绝即带原因暂停）；成员不调用该 manifest 的任何单个阶段（工具没有阶段切片入口），只对 captain 产出的阶段结果做复核、互证与验收。表中「责任面」列写 `manifest` 的行只能由 captain 执行，写 `团队` 的行由成员产出。

| 任务 | 主题 | 责任面 | 负责人 | 依赖 |
|---|---|---|---|---|
| t1 | 交底书理解：PFIE 四元组 + 发明点分级（成员自读，校验 manifest 的 `merge` 结果） | 团队 | 撰写员 | — |
| t2 | 现有技术检索：对比文件 + 布局依据（校验 `search`/`prior_art_filter`/`novelty` 结果） | 团队 | 检索员 | t1 |
| t3 | 附图与附图标记表：按图面类型出图（`generate_patent_figure`，标号随 `labels[]` 内嵌；三维模型走 `generate_structure_figure`）、外部 SVG 标号回填（`add_patent_figure_references`，仅自绘/外部来源图需要）、图文双向一致性核验（`validate_specification` + `analyze_patent_figure`），产出 `figure-deliverable.md` | 团队 | 制图员 | t1 |
| t4 | 披露链执行：`preprocess` → `eligibility` → `extract_problem/features/effects` → `merge` → `groundedness` → `consistency` → `generate_keywords` → `time_baseline` → `search` → `prior_art_filter` → `novelty` → `citation_check` → `report` → `claim_strategy` → `draft_claims` → `figure_analysis`/`figure_analysis_parse` → `draft_specification` → `spec_check` → `enablement_report` → `claim_breadth` → `slop_clean` → `draft_review` → `legal_gaps`，停在 `review_gate` | manifest | captain | t2, t3 |
| t5 | 权项复核：只读 `claim_strategy` 策略表与 `draft_claims` 草稿，核对特征编号、原文锚点、多路从权引用方向；指出越界或漏特征，**不重写权项** | 团队 | 申请人代理 | t4 |
| t6 | 说明书互证：`enablement_report`（A26.3 充分公开）与 `claim_breadth`（A26.4 概括范围）逐条复核，核对实施例摘录与原文锚点 | 团队 | 对立审查员 | t4 |
| t7 | 技术真实性核验：实施例、效果数据、参数合理性（与 t6 并行，输入不同） | 团队 | 技术专家 | t4 |
| t8 | `draft_review` 结果处置：按回退类别定位返工面（`draft-review:enablement`/`support`/`amendment`→说明书，`clarity`→权项，`unity`→策略），由 captain 重跑 manifest 对应段；两轮后仍有争议交人工复核 | 团队判定 + manifest 执行 | captain | t5, t6, t7 |
| t9 | 过 `review_gate`（HITL 确认权项布局与说明书）并重跑收口 | manifest | captain | t8 |
| t10 | 正式文档输出：权利要求书+说明书（claims-spec 渲染），矫正 + 美化 | 团队 | 文档专员 | t9 |
| t11 | 交付收口：产物登记 + HITL 放行 | 团队 | captain | t10 |

返工纪律：t8 的返工**只能重跑 manifest**（重跑时审批门再次询问用户；`approveStageIds` 只在关闭 `approveStageGates` 的部署使用，本部署传入会被拒绝），成员不得手写替换说明书或权利要求。成员的职责是判断「缺哪一类、由谁解释」，不是代写。

`slop_clean` 是 warn 级：未通过只报告，不阻断交付，不得据此打回。质量判定由 `spec_check`/`enablement_report`/`claim_breadth` 承担。

附图信息的消费侧：附图与附图标记表服务于说明书侧的一致性核验（细则 21.2 双向一致），**不作为权利要求撰写的输入**——附图对权项质量没有增益，却会把说明书的表述带进权项范围；权项范围由交底书技术特征与检索结论决定。

### 场景三：答复审查意见包（7 成员）

成员：检索员、撰写员、对立审查员、技术专家、申请人代理、制图员、文档专员。撰写团队可直接延续（同成员不重建）。目标：OA 答复并以正式意见陈述书交付。

执行面分工同场景二：`patent_oa_response_v1` 由 captain 一次跑完（`tighten`、`slop_gate`、`adversary-review` 都是 manifest 内阶段，成员的职责是确认方向、解释结论与验收交付稿，不是自行删减或改写）。

| 任务 | 主题 | 责任面 | 负责人 | 依赖 |
|---|---|---|---|---|
| t1 | OA 解析与问题识别（A22.2/22.3/26.3/26.4/33 等）：成员自读通知书，核对 manifest `parse` 的驳回类型与引用文献 | 团队 | 撰写员 | — |
| t2 | 法条与审查标准核验：核对 `claim-chart` 要素对照的引用与结论 | 团队 | 对立审查员 | t1 |
| t3 | 修改方案与争辩策略（HITL 确认）：确认 `response-plan` 的策略表是否符合本案判断 | 团队 | 申请人代理 | t2 |
| t3a | 附图修改执行与标号一致性核验：按已确认的修改方案改图（附图修改同样受 A33 约束）、自绘/外部 SVG 用 `add_patent_figure_references` 回填标号、`figure-deliverable.md` 落盘 | 团队 | 制图员 | t3 |
| t4 | 答复链执行：`dispute-framing` → `parse` → `dispute-framing-refine` → `claim-chart` → `response-plan` → `adversary-model` → `generate_keywords` → `draft` → `tighten` → `slop_gate` → `adversary-review` → `response_check` → `amendment_basis` → `legal_gaps`，停在 `approval` | manifest | captain | t3, t3a |
| t5 | 计划与对立模型解释：说明 `response-plan` 的逐项策略与 `adversary-model` 列出的薄弱点在定稿中如何回应；未回应的薄弱点列为返工依据 | 团队 | 对立审查员 | t4 |
| t6 | 技术真实性核验：事实、数据、实施例（与 t5 并行，输入不同） | 团队 | 技术专家 | t4 |

## 创建序列

**建队前不做案卷勘察。** 组队所需的事实取自用户本轮的说明：案卷背景、作业类型、当事人与交付件在用户的话里已经够了。案卷结构、交底书、权利要求原文由成员在各自任务里读——他们本来就在并行读同一批文件。captain 在建队阶段最多确认一次案卷根目录存在（一条 `ls`），不得通读材料：实测一次真实建队把 49 条 `bash` 勘察挡在成员就绪之前，首个成员在 24.7 分钟后才出现，而那批文件成员随后又各读了一遍。

1. `patent_teams_create`：name 用 `patent-team-<案卷号>`，description 写明案卷、作业类型（立案/撰写/答复/补正/复审/无效/诉讼）与案卷根目录。
2. 按场景角色包依次 `patent_teams_add_member`（先中立/通用角色，后对抗双方，最后裁判；制图员与文档专员为流程中立角色，随中立角色一并加入——制图员负责附图与附图标记表，文档专员负责收口前的正式文档输出）。
3. `patent_teams_create_task` 按对应场景 DAG 建任务，显式标注 dependencies；调度器自动按依赖分派给空闲成员。
4. 向成员发送案卷上下文：案卷背景、案卷根目录、必读材料路径、产出落盘路径（角色职责契约已由 `add_member(role=...)` 写入成员 persona——立场、输出必含字段、越界禁止、是否触发 HITL；无需再发全文角色简报）。

## 派工纪律

成员 persona 已内置作业纪律（检索先于结论、`source_path` 溯源、法条核验、逐特征比对、免责声明、期限走工具、受阻上报不重试、提交前自检）与角色契约。派工文本因此只写本案事实与验收要求，**不复述纪律与契约**：复述既重复占用双方上下文，又会让成员把常设规则误读成"本次任务的要求"。每一条任务描述按五段写，缺段即视为派工不完整：

- **目标**：这条任务产出什么、给谁用（一句话）。
- **输入**：必读材料的具体路径（案卷背景、交底书、对比文件、上游产出）与要核的法条／判例。
- **产出**：落盘路径与文件名（按 `patent-workspace-layout` 的目录约定），以及必须包含的字段。
- **验收**：通过标准（字段齐、来源可溯源、自检已跑）与自检工具。
- **禁止**：本条任务特有的越界（如「不改实体结论」「不代对方起草」），并附「受阻即上报，不重试、不绕过工具」。

两条配套纪律：

- 通道：派工、追问、催办一律走 `patent_teams_send_message`，状态变更走 `patent_teams_claim_task` / `patent_teams_update_task`。插件已对成员隐藏通用 `send_message`，派工文本不必再交代通道；captain 自己也不要用它——通用 `send_message` 由 `@deepseek-ai/dsh-tool-subagent-control` 注册、解析对象是受控 subagent，它送出的消息既不进团队邮箱、也不进团队事件日志与看板，等于没有记录。
- 被阻塞的任务不催办：依赖未全部完成的任务成员 claim 不了（插件报 blocked），此时下发派工消息或催办只会换来「未 claim、待命」的空转回执；依赖完成时 `patent_teams_wait` 会唤醒你，醒来先用 `patent_teams_status` 确认状态，再派工。
- 团队规模宁小勿大：用户已明确要求组队、且「多角色互证能实质降低风险」的案子才组队（全流程撰写、OA 答复、无效／复审、侵权比对）；任务数少、单一技能通路（单纯形式复核、单幅附图重绘）即使用户要求组队也先说明不必建队，用户坚持则按最小角色集建队。本所一次 7 人团队 + 15 任务 + 13 条裁决 + 51 条消息的产出仍被用户否，规模不是质量。
- 收敛：同一条纪律连续两次被成员违反，先检查任务描述与 `role` 是否错配（角色契约才是纪律的载体），再补派工文本。不要把纪律在派工文本里越写越长。

### 执行面纪律（撰写与答复场景）

`patent_workflow_run` 只有「整 manifest」与「graph」两条路径，`approveStageIds` 只在关闭 `approveStageGates` 的部署用于跳过已批准的审批门（本部署开启时传入会被拒绝），没有「只跑某几个阶段」的入口；`flexible_plan` 的 `run` 只执行调用方自定义的 stage，不是内置 manifest 切片。因此：

- **执行权单向**：captain 用 `patent_workflow_run` 跑完整 manifest 到审批门，前台运行在门前取用户决策（放行继续，拒绝暂停；后台运行仍暂停，需带 `approveStageIds` 重跑），成员只读该次运行的阶段产出。成员不得声明「已执行 `claim_strategy`」「已跑 `tighten`」——它没有这个入口，声称执行只会掩盖手写产物。
- **成员动作用词**：复核、互证、验收、解释、判定返工类别。不写「代写」「补写」「重排」说明书或权利要求。
- **返工只能重跑**：需要改写说明书、权利要求或答复正文时，由 captain 重跑 manifest，重跑时由用户在审批门再次放行。成员手写的替换稿不进交付链，因为它绕过了 `claim_strategy`/`draft_claims` 的确定性渲染与 `spec_check`/`enablement_report` 的判定。
- **派工「禁止」段的固定末句**：任务派工文本须附「不自行执行或重跑 manifest 阶段；发现缺口即上报类别，不重试、不代写」。

## 等待纪律

派活之后**不要**用 `sleep`、后台 job 轮询或反复 `patent_teams_status` 来消磨时间：轮询会把队长的每一次等待都钉死在轮询间隔上，成员干完活在队长发现之前要白等一整个周期。正确循环是**派活 → `patent_teams_wait` → 醒来读 `patent_teams_status` → 再派活**。

- `patent_teams_wait` 阻塞到团队下一次变化为止——任务状态迁移、成员来信、名册变化、成员开工或收工——随即返回，所以正常情况是秒级返回，而不是等满超时。队长专用；成员由调度器唤醒，不需要它。
- 等待时长由 `patent_teams_wait` 的 timeout_ms 参数给出：默认 30000，可设 10 秒 ~ 1 小时。**超时只说明该窗口内没有任何人推进**：据此派活、接管，或把裁定交给用户，不要对同一件事再等一轮。
- 它从不唤醒成员，也不会替你做事。若超时且成员都空闲，先确认是不是该 `patent_teams_send_message` 唤醒成员，还是该自己收口。
- 等待期间成员来信照常投递并会立刻唤醒等待；即便如此，醒来后仍要重读 `patent_teams_status`——持久状态才是唯一事实源，不要凭记忆推进。
- 一次只等一件明确的事：依赖链长时用小窗口多轮 wait，而不是一次等满上限；`ask_user_question` 与 wait 都不要设成小时级，否则夜间无人值守时整条链会被钉死。

## 任务状态与角色约束

任务状态只能按序迁移，跨状态提交会被插件拒绝（错误信息会给出允许的下一步）：

| 当前状态 | 允许迁移到 | 说明 |
|---|---|---|
| `pending` | `claimed` / `cancelled` | 依赖未完成时不可认领 |
| `claimed` | `in_progress` / `failed` / `cancelled` | 认领后先进入 `in_progress`，再提交 `completed` |
| `in_progress` | `completed` / `failed` / `cancelled` | 完成时才提交 output |
| `completed` / `failed` / `cancelled` | — | 终态不可再改；重做走 `patent_teams_reassign_task` |

- captain 不是团队成员：`assignee` 只接受成员名，不能传 `"captain"`；需要 captain 接手时用 `patent_teams_reassign_task(assignee="captain")`，该入口是唯一允许 captain 作为承接者的地方。
- 一个成员同时只能拥有一个未完成任务；成员交付前先 `patent_teams_claim_task` 取 attempt_id，`patent_teams_update_task` 必须带当前 attempt_id（任务被接管后旧 id 失效，须重新认领）。

## 协作纪律

- 单一事实源：团队任务状态只是投影，事件日志与案卷产物落盘（`_matter-log.md`）为唯一事实源；成员完成即回报 captain。
- 恢复点：captain 在案卷目录维护 `progress.md`，只记「目标、当前阻塞原因、下一步」三项，每轮 `patent_teams_wait` 醒来或重新接管时更新；任务状态与成员名单以 `patent_teams_status` 为准，不复制进台账，台账也不进交付物。
- 立场配对：复审/无效 = 请求方（申请人代理/无效请求人）× 防御方（专利权人）+ 合议组（裁判）；诉讼 = 专利权人（原告）× 被告代理人（抗辩）+ 裁判（裁决）+ 调查官（技术查明）。每个立场一个成员，不合并；对抗意见冲突由 captain 收口并说明取舍理由。
- 角色边界：技术专家不评法律论证，代理人/请求人/被告不代写对方文书，裁判不参与任一方策略起草，案件管理员不评技术内容；文档专员**不改实体结论**（权利要求布局、无效理由组合、诉请金额等仍归对应角色与 HITL），只做文本组织、矫正与美化；制图员是图面与标号的唯一权威源，**不改实体结论**（权利要求布局、保护范围、修改方案仍归对应角色与 HITL），也不评新颖性/创造性。
- 期限与流程：答复期限、复审 3 个月与恢复窗口、补正期限、送达推定日（+15 日）由案件管理员或 captain 核验，禁止心算。
- HITL 确认点不可跳过：组队方案、权利要求布局、修改方案、无效理由组合、诉请金额、答复策略按「人工确认点」一节先确认再动手，成员阶段产出在进下一阶段前汇总给用户过目；文档专员交付放行与收口放行合并为一次 ask_user_question，不重复打扰。
- 质量门禁：契约化任务（创建时指定 worker）完成后须过组合质量门禁（worker 契约字段 + 内容充分性 + patent-rule 规则；`patent_eval` 综合评分仅作反馈提示），未过按 `gate_feedback` 修订后重新提交；反复未过由 captain 用 `patent_teams_reassign_task` 处理。文档专员任务（`patent-document-renderer`）同样按契约验收：交付场景/矫正清单/渲染产物缺一即打回。制图员任务（`patent-illustrator`）按契约验收：附图文件/附图标记表/图文一致性/形式要件核验缺一即打回。
- 撰写与答复的实体判定以 manifest 记录为准：`spec_check`、`enablement_report`（A26.3）、`claim_breadth`（A26.4）、`draft_review`（按类别回退）、`response_check`、`amendment_basis`（A33）的通过状态进交付依据；`slop_clean`（披露链，warn 级）只报告不阻断，`slop_gate`（答复链）未过会回退 `draft` 重写。
- 文档交付：正式文档按专利文书输出规范（`patent-document-polish` 技能）走场景→模板映射，渲染 html/pdf（或 docx，officecli 可用时），产物登记 `_matter-log.md`；附图以制图员产出的附图附件页随附（`figure-deliverable.md` 列明各图路径与图号），交付说明里写明附图是渲染文档之外的独立附件——`render_patent_document` 的模板只承载附图说明文字，不嵌入图片。
- 收口必经：每个场景的最终收口任务必须包含 `patent_workflow_run`（按场景 manifest：立案=patent_patentability_v1、撰写=patent_disclosure_v1 并跑到 `review_gate` 放行、答复=patent_oa_response_v1 并跑到 `approval` 放行、复审=patent_reexamination_v1、无效=patent_invalidation_v1、诉讼=patent_infringement_v1）；交付依据是 stage 记录，不是口头结论；补正类无内置 manifest 入口，以替换页逐项核验记录替代。
- 收口：全部任务完成后 `patent_teams_delete` 归档团队；归档保留完整成员与任务历史，可随时复查。
