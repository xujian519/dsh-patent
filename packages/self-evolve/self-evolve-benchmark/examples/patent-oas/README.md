# patent-oas Example Benchmark

English | [中文](README.zh.md)

A patent-practice example benchmark for `@deepseek-ai/dsh-self-evolve-benchmark`, benchmark id `patent-oas`. Each case keeps the public `statement` (the task a target agent sees) physically separate from the private `rubric` (the scoring standard), honoring the engine's statement/rubric isolation (C2): executor, optimizer, and applier roles see only the statement; only the evaluator receives the rubric.

## Cases

| case | task | scored dimensions |
|---|---|---|
| `oa-answer` | Office-action response: search → distinguishing features → actual technical problem → technical teaching → conclusion → claim amendment (six steps) | distinguishing features, technical problem, teaching, conclusion and statute, search and format, amendment grounding |
| `claim-drafting` | Disclosure → claims: independent claim + dependent claims + reference relationships | essential features, scope, dependent layout, reference hierarchy, form and support |
| `disclosure-drafting` | Disclosure → claims + specification (five sections and abstract), with undisclosed detail deliberately left out so A26.3/A26.4 can be graded | essential features, scope, dependent layout, reference hierarchy, form and support, enablement, claim breadth supported |
| `infringement-comparison` | Infringement comparison: all-elements + doctrine of equivalents, per-feature comparison + risk rating | comparison completeness, equivalents, conclusion clarity, risk rating, legal basis |
| `novelty-creative` | Novelty/inventiveness analysis: A22.2 separate comparison + A22.3 three-step | separate comparison, distinguishing features, technical problem, teaching, conclusion and statute |

Each case directory holds exactly `statement` and `rubric`; a multi-round case adds one `rounds/02/statement` file:

```
cases/<case-id>/
├── statement             # 公开的第 1 轮任务文本 —— 目标 agent 唯一可见的输入
├── rubric                # 私密评分标准 —— 与 statement 物理隔离
└── rounds/02/statement   # 可选:第 2 轮脚本化审查意见
```
`disclosure-drafting` is the only case that scores A26.3 and A26.4. Its disclosure deliberately leaves one route unimplemented (a model-based variant with no structure, data, or labelling) and gives two concrete routes for the claimed generalization, so a deliverable that copies the unimplemented route into the independent claim loses the enablement dimension. The checked-in sample is synthetic: the planned corpus of 15 pieces (10 de-legalized granted texts and 5 real disclosures with attorney revisions) is not in the repository. Real client material cannot be committed, and fabricated "real" samples would misstate the measurement, so the gap is recorded instead. Synthetic disclosures overstate patent idiom and understate how much scope a drafter can recover from a fragmentary disclosure; scores from this case do not stand in for that corpus.

Multi-round cases are fixed at two rounds: the executor answers, receives the scripted review opinion as new public input, and revises the previous deliverable, which the runner hands it as `previous-deliverable.md`. The same rubric scores both rounds; the gate judges the final round only. Keeping the review opinion in the case makes the second turn reproducible instead of introducing a second, varying reviewer model.

`patent-state/guidance.md` is the initial agent-state seed: a model-visible patent work specification (checklist) that executors follow and the optimize loop edits. It holds only general working method, never any case answer, and does not break rubric isolation.

## Problem-space DAG and regression gate

`problem-space.yaml` models the patent-practice problem space this gold standard covers as a directed acyclic graph: nodes are the facets a deliverable is judged on, `dependsOn` edges carry the prerequisite structure (search precedes distinguishing features, distinguishing features precede the actual technical problem, per-feature comparison precedes equivalents), and each rubric dimension is split by its own points onto the nodes it observes. `gate.yaml` pins the gold-standard digest and the score thresholds.

`pnpm run verify-patent-oas-gold` (CI, no key) checks that the gold standard and the DAG stay mutually pinned — every rubric dimension mapped, mapping weights equal to the rubric's own points, every node observable, no cycle in the prerequisite edges — that the recorded gold digest matches, and that a recorded baseline can satisfy its own thresholds. `--run <record.json>` judges one recorded run against the thresholds and attributes failures to problem-space nodes, printing per-case and per-node range and sample standard deviation when the record keeps per-run scores; `--accept <record.json>` promotes a validated run record to the baseline, requiring every case to carry `retrieval` so a legacy record cannot silently reset the baseline to an unlabelled setting; `--write` re-records the gold digest after a deliberate gold edit.

A run record is the contract between measurement and the threshold: it stores only the raw per-dimension observations, and the gate derives case and node scores from the DAG so no second copy of either can drift. Its fields are `{ benchmarkId, recordedAt, execution?, workflowId?, runsPerCase, provider?, modelId?, cost?, tokens?: { input, output }, cases: [{ caseId, retrieval, dimensions: [{ index, label, points, score, scores? }], rounds?: [{ round, statementDigest?, dimensions: [{ index, score, scores? }], deliverableDigests, claimVersions?, concision? }], concision? }] }`. `retrieval` is the case's retrieval setting: `oracle` puts the comparison documents in the statement (`oa-answer`, `novelty-creative`), `none` means the case needs no prior-art retrieval (`claim-drafting`, `disclosure-drafting`, `infringement-comparison`), and `simulation` reserves a controlled-corpus run. The gate rejects a comparison whose per-case setting differs from the baseline's, because a search-quality score and an oracle-answer score cannot share thresholds; a record without the field compares only with a baseline that also lacks it. The runner still writes a capture whose setting differs from the baseline's, but skips the verdict and exits non-zero; no simulation corpus is recorded yet, so a `simulation` run has no baseline to compare against. `execution` is the measured surface: `prompt` is the profile's prompt call, `workflow` runs the manifest named by `workflowId`; the surface is recorded once per capture because one capture starts one kind of process. A record predating the workflow surface omits the field and reads as `prompt`, since that collector had only the prompt path; a `workflow` record must carry `workflowId`, and every case it observes must declare that manifest in `problem-space.yaml`. With `runsPerCase > 1`, `scores` keeps one raw score per run so a reader can recompute variance and intervals instead of trusting a lone mean; `tokens` and `cost` sum every call in the capture (`tokens.input` is billed input, with cache reads and writes folded in), with `cost` taken from the provider when every call reports it and otherwise converted from the tokens at the caller's per-million prices; a capture where only some calls report usage omits the total instead of recording a partial one. The single input price covers all billed input, cached tokens included; a caller that prices cache separately reports cost from the seam instead. For a multi-round case, `dimensions` is the final round while `rounds` keeps every round's per-dimension observation, the digest of the scripted review opinion that opened it (`statementDigest`; round 1 has none), each run's deliverable digest for that round, and — under the workflow surface — each run's `claimVersions`: the depth of that round's deliverable on the `_matter-log.md` supersede chain, recomputed from the log rather than reported by the executor. The chain must advance in every round, so a round whose entry supersedes nothing reads as two rounds on one claim set. The gate still judges the final round and prints the per-round totals, so whether a revision improved or regressed is visible without changing the decision rule. `concision` records how long each deliverable is — `{ proseChars, budget?, overBudget?, paragraphs, sections, emptySections, repeatedSentences }`, one entry per run — and it is **observational only**: no dimension, node, case or aggregate score reads it, so a longer answer still costs nothing on that axis. It hangs off a round for multi-round cases and off the case itself for single-round ones, which is where the other per-run observations already live. `proseChars` counts the same visible characters as the `slop-gate` and `tighten` stages but drops table rows first, because the OA response budget excludes tables and claim text and counting them would flag every compliant answer; `budget` is the case's own declared budget (`oa-answer` takes the manifest's 4000), and the gate only checks that `overBudget` equals `max(0, proseChars - budget)` — a hand-written number is not taken on faith. `gate.yaml` declares one baseline per surface under `baselines`, keyed by `execution` and `workflowId`; `--accept` and `--run` route a record to its own surface's baseline and refuse a surface nothing is declared for, so a workflow score is never judged against prompt thresholds. The prompt baseline lives at `packages/self-evolve/evaluation/patent-oas-baseline.json`. While a declared baseline file is absent the gate exits non-zero and prints the command that records one, so an absent regression layer and a passing one never share an exit code; the fork's required CI lane runs the gate, which is what carries that exit code to a pull request.

`pnpm run gate:patent-oas` captures a measurement. `--dry-run` prints the plan (cases, rounds, runs, total agent calls, and under the workflow surface the stage count per round and the total stage runs) together with the capture's wall-clock budget and per-call timeout, without any model call; a real run needs `DEEPSEEK_API_KEY` (or a `.env` declaring it) and skips with exit 0 without one. It starts one `dsh --profile` process per call — one executor per case round, working in a private copy of the agent state and writing its deliverable to `deliverable.md`, and one evaluator per rubric dimension in each round, writing a `{"score": n}` JSON object to `score.json` — then writes the run record, keeps every artifact and agent log under `.artifacts/patent-oas/<stamp>/`, and judges the run against the thresholds. A multi-round case's second round runs under `run-N/round-2/`: the runner copies the first round's agent state, keeps its deliverable as `previous-deliverable.md`, and removes the old `deliverable.md` and `agent.log`, so the executor must write a new deliverable and the logs stay per-round. Under the `headless` profile every call also runs with `--json`, so the runner reads the `step_end` usage events and sums the capture's tokens. `--case <id>` and `--runs <n>` narrow and repeat a run; `--timeout-ms` caps one call and `--budget-ms` the whole capture; `--input-usd-per-mtok` and `--output-usd-per-mtok` supply token prices when the provider reports usage but no cost; the repository keeps no price table, because prices vary by contract and a checked-in number would silently age. the baseline is promoted by the gate, not by the runner.

`--execution workflow` changes the measured surface, not the prompt: the runner adds `patent-workflow.patch.yml` to every `dsh` call, and the executor answers each round through the product's own surfaces — one `patent_workflow_run` call over the manifest `problem-space.yaml` declares for that case, then one `matter_log_append` entry. Stage order, upstream hand-off, and the `requireAllSteps` verdict stay inside the workflow engine; the runner names no stage of its own. Which stages compose the deliverable is a per-case declaration in `problem-space.yaml` (`workflowDeliverable`), because the same manifest can deliver a response, or claims plus a specification: `oa-answer` takes `draft`, `disclosure-drafting` takes `draft_claims` and `draft_specification` in that order. The executor re-saves those stage outputs verbatim into `outputs/<artifact>-r<N>.md`, which is the file scored per dimension. Approval gates are passed explicitly by stage id (`approveStageIds`) because the capture is unattended and an interrupted run is not a completed one; skipping a stage is not offered — the run record is read back and a capture whose workflow degraded or paused fails instead of being scored. Per-round deliverables are saved under new paths so the supersede chain advances, and the case id is pinned per run (`patent-oas-<case>-run<N>`), so claim versions recompute from the log rather than from what the model says it did. `patent_workflow_run` takes the claims under review in `claims`, separately from `input`: an element-level stage without `claims` splits the whole `input` into claim segments by leading numbering, and the office action's enumerated arguments and step list are exactly that, so every verbatim substring check fails.

Each measured surface is judged only on the cuts it can produce evidence for. A `workflow` record must cover the cases that `problem-space.yaml` declares this manifest for — no other case can run it, so requiring the full gold set would leave this surface permanently unable to record a baseline. `surfaces` in `gate.yaml` can also lift a node out of the verdict for one surface: an exempted node leaves the node, case and aggregate weightings together, and the verdict prints a `[not-assessed]` line naming the exemption. Declare it only where the manifest structurally produces no evidence for that node; a low score is not a reason to exempt, and a policy that exempts every assessable node of the surface is rejected by the gate. None is declared here: `patent_oa_response_v1` generates retrieval keywords in its `generate_keywords` stage and the `draft` guidance puts that strategy into the deliverable, so `prior-art-search` and `deliverable-format` are read from real evidence on both surfaces.

Cost accounting: a workflow round executes the whole manifest — 15 stages, five of them model-backed, for `patent_oa_response_v1`, and 27 stages, 14 of them model-backed, for `patent_disclosure_v1` — which makes one capture roughly an order of magnitude more model calls than one prompt round, so `--runs` defaults to 1 under this surface; `--budget-ms` still caps the whole capture and the plan line prints the stage count before anything is spent.

A captured score measures the model plus the work specification under the profile the caller passed (default `headless`) and, under the workflow surface, without the preset's persona and skill layer — a preset is agent-plane and only `dsh-agent-preset-registry` can mount one, which the headless composition does not run. Records are comparable with each other only under the same profile and the same surface, which is what the `provider`, `modelId`, `execution` and `workflowId` fields are for.

The checked-in prompt-surface baseline is one keyed measurement recorded on 2026-11-02 under the `headless` profile with `--provider deepseek-official --model deepseek-flash`, three runs per case across five cases. The new case's A26.3 and A26.4 nodes read 89.0 and 87.7, and its claim-scope node reads 96.8. The run follows the `--runs=3` set by the B7 measurement protocol. Everything except the model calls is covered keylessly as well: the capture seam is injectable, and the specs drive the whole pipeline with a stub that writes the two artifacts, covering the prompts, the artifact contract, the dimension-wise aggregation, the two-round handoff, the launcher arguments, and the record's acceptance by the gate. ## Seeding

```sh
node seed.mjs [baseDir]
```

`baseDir` defaults to `~/.dsh/self-evolve-benchmark`, aligned with the engine's default `baseDir` (`$DSH_HOME` overrides `~/.dsh`). The script is idempotent: re-running overwrites case files in place.

Seeded layout:

```
<baseDir>/benchmarks/patent-oas/
├── benchmark_config.yaml
├── oa-answer/statement|rubric
├── claim-drafting/statement|rubric
├── disclosure-drafting/statement|rubric
├── infringement-comparison/statement|rubric
└── novelty-creative/statement|rubric
<baseDir>/patent-state/
└── guidance.md   # 初始 agent state 种子
```

## Usage

After seeding, drive the loop through the engine's public methods. Point the engine's `baseDir` at the same data root and `agentStateDir` at the seeded `patent-state` work copy:

```ts
await engine.establishBaseline('patent-oas', { runsPerCase: 1 })
await engine.optimizeLoop('patent-oas', {
  maxRounds: 3,
  targetScore: 80,
  runsPerCase: 1,
})
```

`agentStateDir` defaults to the `patent-state` work copy (see the patent preset assembly); **never** use a real docket directory as `agentStateDir` — that would snapshot real work product in full and let the optimize loop rewrite it in place.
