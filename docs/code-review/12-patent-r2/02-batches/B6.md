## 审阅方法

- 导出可达性：反向解析 43 个文件的每个模块级导出，统计生产代码与测试消费者；对零生产消费者的导出回源确认是否属基线锁定的公开面。
- 消费者跨包核对：`patent-tools/src/wiring.ts` 是这两个包的唯一生产消费者，逐个核对服务方法与通道工厂的接线路径（含 `existsSync` 判定分支）。
- 静态清单：`new Error(`、`catch`、`as unknown`、`as string`、`TODO`、`skip` 逐条回源；`v8 ignore` 只核对其存在理由，不新增。
- 高风险路径精读：`ego-session` 的环境白名单与输出截断、`subprocess-runner` 的计时器、`cnipr-channel` 的排队/取消/收据缺失、`patsnap-channel` 的重试与期限、`patent-cache` 的 TTL/LRU/在途合并、`kg-store` 的 schema 探测与 FTS 降级、`knowledge-law-search` 的时间效力 SQL 与参数顺序、`install` 的裁剪与压缩、`wiki-card-loader` 的扫描缓存失效。
- 配置与默认值：逐字段核对 `Config` 的 schema 约束、构造期复验与运行时消费点是否一致。
- 未委派子代理。

## 已排除候选

| 候选 | 排除理由 |
|---|---|
| 三份相同的号码归一化实现：`ego-session.ts:286`、`patsnap-receipt.ts:31`、`patent-tools/src/tool/patent-pdf-download.ts:224` | 三者实现一致（trim → upper → 去 `\s-:/`），但 `patsnap-receipt.ts` 是纯函数层，`ego-session.ts` 带 `node:fs`/`node:os`；合并会让纯模块依赖会话模块，或为 3 行函数新增一个模块。两个名字又都被公开面基线锁定，第三份在 `patent-tools`（B9–B12 范围）。 |
| `patent-tools/src/tool/patent-kg-query.ts:22` 自带的 `CITE_RELATIONS` 与 `patent-kg-adapter.ts:35` 的同名集合重复 | 集合内容逐项相同；副本处注明原因：插件入口只允许导出名称、配置、类型与服务类，不能为共享该常量新增值导出。属插件入口规则的直接后果。 |
| `install.ts` 给 `documents` 加 `search_prefix`/时间效力列却不 bump `KNOWLEDGE_DB.version` | 两处新增都是可空列，读取端（`knowledge-law-search` 的 `projection()`、`case-law-search` 的 `pragma_table_info` 探测）逐列判定存在性，缺列与有列都能安全解释；版本号用于拒绝不可安全解释的旧结构，这里不构成。 |
| `readCniprPdfLinksPayload` 不按 `CNIPR_PDF_URL_PATTERN` 复核 `matches` | 载荷来自本包生成的脚本，`normalizeCniprPdfUrls` 已强制 `http://` 前缀并去重；把「脚本产物」当敌对输入校验属重复防御，且真正的 URL 校验在下游下载工具。 |
| 模块注释位于 `import` 之后（`cnipr-receipt.ts`、`patent-kg-adapter.ts`、`wiki-card-loader.ts`、`kg-store.ts`） | 纯排版；全仓仅 `cnipr-receipt.ts` 与 `prompt-hygiene.ts` 属「有 `@module` 但不在首行」，其余三处根本没有 `@module` 段，属未写而非错位。统一改动是无收益的大范围重排。 |
| `WikiCardLoader` 正文缓存按插入序淘汰（FIFO）而非 LRU | 类的文档只说「内容缓存上限 64 条」，未承诺 LRU；卡片正文读取分布均匀时两者差异可忽略。 |
| `resolveKnowledgePaths` 在三个候选路径都不存在时静默返回 `<dataDir>/knowledge.db` | 解析只定位路径，不打开库；真正的缺库判定在 `openKnowledgeDb` 的 fail-loud（`KnowledgeDbVersionError`），工具据此报错。 |
