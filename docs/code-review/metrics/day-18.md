## 逐条说明

### P-RET-01 超时：已恢复

首次调用按注入返回 `tool_timeout`，没有进入检索。恢复调用把 `limit` 从 2 降到 1，命中 1 条，`docType` 为 `case`，`via` 为 `fts`，`dbPath` 正确。题面的「不超过 2 条、每条 case、至少 1 条有决定号或案号、via 为 fts 或 like、点名库路径」在恢复后全部成立。

注入点选在工具边界，记录的是恢复计划本身，不是 `patent_case_search` 对上游超时的内部处理。工具对上游失败的处理路径另由 P1 的直接调用层覆盖，本层不替代它。

### P-RET-01 空结果：已恢复，并暴露假闭环风险

首次调用成功，`total=0`、`results=0`。如果只看 `tool/result` 的非错误状态，这次调用会被写成「完成」；但题面的外部判定要求至少 1 条命中，实际不成立。跑分器把它记为「工具成功、外部判定不成立」，没有记闭环。

恢复调用同样把 `limit` 从 2 降到 1，命中 1 条，外部判定成立。这一条是 [10-tool-metrics-plan.md](../10-tool-metrics-plan.md) 中「`tool/result` 非错误本身不算闭环成功」的直接样本。

### P-RET-04 取消：已恢复

首次调用按注入返回 `tool_aborted`。恢复调用把 `limit` 从 3 降到 2、关闭 `include_body`，返回 2 张卡片，全部以 `专利实务/说明书` 开头，标题含「充分公开」，结果里没有专利公开号。题面的四条判定成立。

### 假恢复与重复检查

三次注入都没有在同一工具、同一原始参数上再调用一次；每次只有 1 次恢复调用，低于 2 次上限。恢复后的外部判定由题面字段逐条核验，不是由工具的成功标志推断，因此没有「宣称成功而外部判定不成立」的样本。

## 族内结论

本族 3 种注入全部覆盖，3/3 已恢复；1 次空结果注入属于「成功但外部判定不成立」，说明只看工具错误码会漏掉这类失败。没有同名同参数重复、没有超过 2 次的重试、没有假恢复。

子进程与工具临时目录都是 0；恢复调用读的是 `~/.dsh/knowledge/knowledge-lite.db` 与 `~/.dsh/knowledge/wiki`，没有写业务目录。跑分器自身的 `dsh-subprocess-*` 空 spill 目录在进程正常退出时删除，不计入工具残留。
