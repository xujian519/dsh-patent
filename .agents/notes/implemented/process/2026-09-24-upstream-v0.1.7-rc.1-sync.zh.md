# Agent Note: 上游 v0.1.7-rc.1 同步

Status: implemented

[English](2026-09-24-upstream-v0.1.7-rc.1-sync.md) | 中文

## 问题

本次同步把 fork 的跟踪点从上游的 `dsh-v0.1.7-alpha.2` 标签（即本次合并的基点）推进到 `dsh-v0.1.7-rc.1` 发布。上游前进 156 个提交、涉及 933 个文件（+13851/−3101），fork 自带 656 个、涉及 3555 个文件，合并有 24 个路径冲突：其中 15 个是 `apps/desktop` README 与五份生成目录的中文页、配对记录或英文页，另加 `pnpm-lock.yaml`。

上游有四处改动撞上了 fork 自己写下的内容。桌面工作重写了 `apps/desktop/src/main.ts` 的宿主启动、协议注册与菜单构造，并把一份原生引擎放到更新归档旁边。`apps/cli/src/plugin.ts` 在 fork 的 pnpm 失败提示旁边新增了 profile 版本豁免命令。`packages/boot/app-boot/src/profile.ts`（自动合并进 fork 的副本）现在只在 bundle 自带的 dsh peers 可解析、或该 profile 豁免了这一精确配对时，才接纳这个 profile bundle。两个 client 包收窄了会话节点交给 seat 回调的标识符，会话事件折叠改读 `SessionEventLike`。

## 决定

- **版本族在合并提交内对齐，且由 `constraints` 强制。** 根清单与全部 352 个成员移到 `0.1.7-rc.1`；而只有 fork 发布的 43 份清单在本提交之前仍停在 `0.1.7-alpha.2`：`check-workspace-constraints` 一遍读完树里的每一份清单、要求每份版本等于根版本，因此漏掉一份 fork 专有清单，就会在上游清单根本不会读到的文件上让这道门失败。唯一的版本镜像 `SIDEBAR_SERVICE_VERSION`（已随 PR #677 删除的 better-sidebar 包的 `service.ts`）随它们一起移动；对合并后的清单跑 `pnpm install --lockfile-only` 不改变 `pnpm-lock.yaml`。
- **ACP 语料钉住的握手版本随发布移动。** 9 份 `snapshots/acp/*/stdout.expected.jsonl` 记录握手里的 `agentInfo.version`，而 `packages/acp/acp/src/index.ts` 由自己的清单派生该值，因此每次发版都会打破持有该期望的用例。九处都移到 `0.1.7-rc.1`，`snapshots/acp` 的 keyless 回放 16 个用例通过。这枚手工维护的钉子，以及将退役它的占位符化方案，记录在 `docs/TECH_DEBT.md`。
- **client 冲突取上游放宽的标识符词汇，同时保住 fork 的品牌。** `packages/client/ui-agent-preset/src/client/section-store.ts` 删掉本地 `message()` 助手，三处调用点改用 `dsh-value` 的 `errorMessage`。`packages/client/ui-tool/src/client/tool/ToolCallTree.tsx` 保留 `ToolCallId` 强制转换：它把 chat 节点的字符串 id 带进说自己品牌词汇的 seat 回调。`packages/client/ui-patent-teams/src/client/teams-model.ts` 并未被冲突标记，但它的折叠参数放宽为 `SessionEventLike`，并去掉不再使用的 `SessionEvent` 导入。
- **`plugin.ts` 保留 fork 的 pnpm 失败提示，采纳上游的豁免命令。** `setProfileVersionExemption` 与 `dsh plugin --profile … allow-version … --accept-risk` 提示行来自上游；fork 的 stderr 累积与它的两类失败判据保留，而 git-hosted 那条提示仍指向 profile `package.json` 里的 `pnpm.onlyBuiltDependencies`——本机验证过 pnpm 10 正是从该处施行这份构建白名单，尽管 pnpm 自己的输出指向 `pnpm-workspace.yaml`。
- **桌面冲突保留 fork 的启动序列，采纳上游的引擎打包。** `apps/desktop/src/main.ts` 与它的启动规格按并集解析：上游的宿主 inspect 端口、协议注册与菜单重构落在 fork 的 `onFailure`/`backend.start` 序列与它的 Windows-only 开发者工具菜单项之内，两套用例都保留。`apps/desktop/tests/installed-update-package-content.spec.ts` 取上游夹具：它在归档旁边放置 LibreOffice 引擎，并把它的 `soffice.exe` 加进被重签名的可执行文件。
- **README 与五份生成目录按两父提交的并集解析。** `apps/desktop/README.md` 保留 fork 的产品段落与上游重写的归属、引擎、开发叙述，中文页与配对记录随之跟进。`docs/capability-seams`、`docs/config-catalog`、`docs/event-producer-consumer`、`docs/module-graph` 与 `docs/tool-catalog` 都在已解析的树上由各自的生成器产出；每个被改动的配对通过 `pnpm run verify-translation-pairing --write` 重录 blob 哈希。
- **`packages/bundle/web-app/package.json` 在上游新增的 client 包旁边保留 fork 的 preset。** fork 的 `patent` 与 `document` preset、它们的页面与 `skills` 目录，连同渲染它们的那些包一起留在 `files` 与 `exports` 中，上游新增的依赖条目并排到来。
- **`profile.spec.ts` 同时携带上游的 bundle 兼容用例与 fork 的 pin 套件。** 上游的用例跳过自带 dsh peers 不兼容的 bundle，直至该 profile 豁免这一精确配对；fork 的 `ensureProfileVersionPins` 用例保留。两父提交在同一位置各自加用例，因此这里按并集解析而非在两侧之间做选择。
- **作为史实或夹具的版本串保持在 `0.1.7-alpha.2`。** `docs/TECH_DEBT.md`、`.agents/audits/2026-09-23-snapshot-lane-and-loader-issues.md`、alpha.2 同步 note 三件套、`apps/desktop/tests/desktop-build-version.spec.ts` 与 `packages/boot/app-boot/tests/plugin-compatibility.spec.ts`，要么把该发布记作历史，要么需要它作为与已发布版本不同的取值。
- **fork 的 vendor-rescope 白名单补入本发布新增的、会触发该门的那一个文件。** `packages/extensions/ui-cordis/src/client/CordisPreparingRow.tsx` 写着 `PropsLocale<'cordis'>`，而这个 `'cordis'` 是该包 `locales.ts` 以 `NS` 导出的 UI locale 命名空间、不是包名，因此 `GENERIC_SKIPS` 豁免它，与该名单已豁免的四个同族 row 文件一致。上游自己的 `scripts/rescope-vendor.ts` 没有这条条目，它的 CI 也不跑这道门，所以只有 fork 的 `hygiene` 会报出这份 residue。

## 后果

fork 带着完整的专利、文档、桌面、better-sidebar、synapse、self-evolve 与插件市场面发布上游的 v0.1.7-rc.1 基线。上游并不发布的 43 份清单，是每次同步都要手工 bump 的集合，而 `pnpm run constraints` 使漏掉其中一份成为不可能。生成目录与桌面 README 是两父提交替换了同一段叙述的文件，因此下次同步仍会把那些冲突读作并集。ACP 握手钉子在占位符化方案落地前，每发一次版就要付九份文件的刷新成本；`docs/TECH_DEBT.md` 仍是 fork 独有的账本，它引用的路径会被 `verify-package-paths` 当作引用读取——其中指向已删除的 `client/connection/src/client/fixture.ts` 的那一行，就是本树携带的唯一门禁失败。

## 考虑过的替代方案

- **只 bump 上游的清单，把 fork 的 43 份留在 `0.1.7-alpha.2`。** 不可行：`constraints` 一遍读完每份清单与根版本比较，而 `scripts/release/verify.ts` 把这 352 个当作单一族解析，部分 bump 会在两处读法上同时失败。
- **在 `plugin.ts` 里采用上游的 `allowBuilds` 提示文本。** 否决：fork 已在本机验证 pnpm 10 从 profile `package.json` 的 `pnpm.onlyBuiltDependencies` 施行 git-hosted 构建白名单，因此上游那行会把使用者指到 pnpm 并不读取的文件。
- **在 `section-store.ts` 里保留 fork 的本地 `message()` 助手。** 否决：`dsh-value` 就是为这次转换导出 `errorMessage` 的，保留助手等于为同一种行为留第二种拼法。
- **在 `main.ts` 上取上游那一侧。** 否决：fork 的这个文件携带自己的启动序列、它的 `onFailure` 处理，以及只在 Windows 上构造开发者工具菜单项的菜单策略，因此上游的重构必须落在它之内。
- **把带发布编号的夹具刷新到新版本。** 否决：`desktop-build-version.spec.ts` 拒斥离开产品发布编号的构建版本，而 `plugin-compatibility.spec.ts` 需要一个既不等于运行时版本、也不是区间的豁免取值；刷新会抹掉每个用例存在的理由。

## 测试

`pnpm run constraints` 要求上游并不发布的 43 份清单版本等于根版本，在合并树上通过。`pnpm run typecheck` 覆盖两个编译面（退出 0），`pnpm run lint` 退出 0、无诊断输出。`pnpm run doc-sync` 报 43 门通过、1 门失败，失败为 `verify-package-paths` 指向 `docs/TECH_DEBT.md:225`，而它引用的路径早于本次合并即已从树中删除；冲突目录上的生成器校验全部通过（`verify-tool-catalog`、`verify-config-catalog`、`verify-doc-graphs`、`verify-dependency-catalog`、`verify-persistence-catalog`、`verify-client-catalog`，以及 `gen-module-graph --check` 报 3 份产物为最新）。`pnpm exec tsx scripts/release/verify.ts --family dsh` 解析 352 个成员、版本 `0.1.7-rc.1`，发布顺序可解。`pnpm exec vitest run --config vitest.snapshot.config.ts snapshots/acp` keyless 回放 16 个用例；`packages/client/better-sidebar` 跑 170 个文件、2071 个用例（另 5 个跳过）；`packages/client/ui-patent-teams` 连同 `apps/desktop/tests/desktop-build-version.spec.ts` 与 `packages/boot/app-boot/tests/plugin-compatibility.spec.ts` 跑 5 个文件、131 个用例；`apps/cli/tests/plugin.spec.ts` 与 `apps/cli/tests/plugin-failure-hints.spec.ts` 跑 18 个用例。`pnpm run hygiene` 的 19 道门全部通过（退出码 0），`vendor rescope` 检查在其中。`pnpm run verify-translation-pairing` 接受每个被改动的配对。
