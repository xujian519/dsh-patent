## 为什么这些检查可以进 CI

- 不依赖模型采样。直接调用由 fixture 给出参数，脚本场景由脚本按题面填参，二者都不经过模型选择。
- 反例可机械判定。非法 JSON、类型错误、缺必填、路径越界、注入字符、超长正文、子进程、临时目录、`error.code`、外部判定与账本数字，都能从退出码、JSON 字段、文件内容或进程状态读出。
- 失败位置稳定。直接调用层的 54 条对抗样本与脚本层的 16 个两步场景都把失败停在参数、文件存在性、内容门或结构校验，没有「执行到一半才发现」的类型。
- 现有记录已经给出反例与通过样本。[day-12.md](day-12.md) 的 15 次调用与 54 条对抗样本、[script-baseline.md](script-baseline.md) 的 12 次注入、[day-35.md](day-35.md) 的 16 个场景都可以直接抽成 fixture。

## 为什么不进阻塞 CI

- 工具选择、拒绝与误拒由模型轨迹决定，脚本没有选择过程；放进 CI 只能测脚本，不能测模型。
- 响应时间含进程启动、模型等待与工具执行，单次波动从 14 秒到 424 秒；用它做阈值会把环境抖动记成产品回归。
- 成本效率依赖 token 单价与真实 API 费用，CI 没有可复现的计费环境。
- 上下文利用率依赖该次请求的工具声明与模型实际调用，属于真实模型层。
- 网络题、本机知识库题、Office Kit 与真实视频账单依赖外部环境；CI 缺依赖时只能跳过，不能把跳过记成通过。

这五项与 [day-44.md](day-44.md) 的周期评测一一对应。本清单没有把响应时间、token 费用或工具选择准确率写成阻塞 CI。
