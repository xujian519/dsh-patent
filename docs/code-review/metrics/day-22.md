## 成功但未闭环的样本

以下 7 次调用的 `tool/result` 不是错误，但按题面外部判定不成立，全部没有记闭环：

- 干净场景 P-RET-02：返回 1 条状态，状态值不满足题面枚举。
- 干净场景 P-RET-03：返回 10 条命中，超过题面的 5 条上限。
- 干净场景 P-LAW-02：返回 3 条，路径前缀不满足题面的「每条」要求。
- 注入轮 4 次空结果：P-RET-01、P-LAW-01、P-CLM-03、P-SPC-02。工具返回成功形状的空结果，外部判定不成立；恢复调用才使判定成立。

这条口径写成数字：本阶段有 7 次「非错误结果、但不算完成」。只看工具错误码会漏掉它们，也正是计划要求「`tool/result` 非错误本身不算闭环成功」的原因。

## 恢复基线

| 族 | 注入次数 | 已恢复 | 未恢复 | 原样重复 | 重试超过 2 次 | 假恢复 |
|---|---:|---:|---:|---:|---:|---:|
| 检索与法律状态 | 3 | 3 | 0 | 0 | 0 | 0 |
| 法条核验与规则 | 3 | 3 | 0 | 0 | 0 | 0 |
| 权利要求 | 3 | 3 | 0 | 0 | 0 | 0 |
| 说明书与立案 | 3 | 3 | 0 | 0 | 0 | 0 |
| **合计** | **12** | **12** | **0** | **0** | **0** | **0** |

12 次注入按题号分布：P-RET-01 超时与空结果、P-RET-04 取消；P-LAW-03 超时、P-LAW-01 空结果、P-LAW-04 取消；P-CLM-01 超时、P-CLM-03 空结果与取消；P-SPC-04 超时、P-SPC-02 空结果、P-SPC-01 取消。每种注入都覆盖了四族，每族 3 次。

恢复判定的三条规则都没有触发：12 次恢复都换了参数或输入表达，没有原样重放；每次只重试 1 次，没有超过 2 次；恢复后的外部判定逐条核验，没有出现「宣称成功而外部判定不成立」。4 次空结果注入的首次调用是成功形状，脚本没有把它的成功当闭环，因此不构成假恢复。

恢复的墙钟范围是 0—116 ms；最慢的是 P-SPC-04 重跑 Python 引擎的 116 ms。这个数只说明恢复调用的工具路径耗时，不是模型等待或响应时间。

## 资源与残留基线

14 次干净调用与 12 次恢复调用都没有留下子进程；`build_patent_filing` 的引擎临时目录 `dsh-patent-filing-*` 在调用返回前删除。跑分器持有的 `dsh-subprocess-*` 空 spill 目录在进程正常退出时删除，属于测量器具而不是工具残留。输出文件只有 P-SPC-04 的两份 docx（干净场景与恢复各一份），按题面落在输出目录；它们不是残留。

知识库以只读方式打开；检索与法律状态题没有写业务目录。本阶段没有发现工具级别的进程或临时目录泄漏。

## 6 题未测口径

P-RET-05、P-LAW-05、P-CLM-05、P-SPC-05 是应拒绝题，只在真实模型层测量；P-CLM-02、P-CLM-04 的 `claim_chart_build` 内部调用模型，脚本层没有模型端口。6 题都不进入本层分母，不记 0，也不记失败。

因此本阶段对 20 题的覆盖是「14 题有外部判定结果，6 题按层未测」。把 6 题记成失败会低估四族，把 6 题记成通过会高估拒绝与工具内模型能力；两种都不做。如果验收要求 20 题都出外部判定，需要 P3 的真实模型层，不能在脚本层补。

## 可进 CI 的检查

本阶段的 10 道闭环成立题里，以下检查不依赖模型，也不依赖网络，适合进 CI：

- P-RET-01 的判例检索需要本机知识库；CI 没有 `knowledge-lite.db` 时跳过，不记失败。
- P-RET-04 需要 wiki 目录；CI 没有时同样跳过。
- P-LAW-01、P-LAW-03、P-LAW-04 只用随包资产，可直接进 CI。
- P-CLM-01、P-CLM-03 是纯函数，可直接进 CI。
- P-SPC-01、P-SPC-02 是纯函数，可直接进 CI。
- P-SPC-04 需要带 `python-docx` 的 Python 解释器；CI 走随包运行时，探测不到时跳过。

P-RET-02、P-RET-03 依赖网络，不进阻塞 CI；P-SPC-03 在题面 fixture 修好之前不能进 CI。注入轮的 12 个检查都是边界注入，不依赖网络与模型，可以随对应题一起进 CI，但必须先修好题面判定，否则恢复后的外部判定仍会失败。
