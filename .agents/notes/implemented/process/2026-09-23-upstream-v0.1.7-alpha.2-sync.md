# Agent Note: upstream v0.1.7-alpha.2 sync

Status: implemented

English | [中文](2026-09-23-upstream-v0.1.7-alpha.2-sync.zh.md)

## Problem

The fork moved from upstream's `dsh-v0.1.7-alpha.1` tag, this merge's base, to the `dsh-v0.1.7-alpha.2` release. Upstream advanced 162 commits across 869 files (+21355/−11052) while the fork carried 598 of its own, and the merge conflicted in 106 paths.

Two changes in this release judge content the fork authors. Upstream retired the `workspace:^` dependency range in favour of `workspace:*` for DSH packages and `workspace:~` for `vendor/` and `native/`, and `check-workspace-constraints` now derives that expectation for every manifest it reads, including the 47 manifests upstream does not ship; 45 of those carried the retired range. Upstream also rewrote the sensevoice worker spec, whose fork-local synchronization had existed only to keep the call-count poll it deletes from racing.

## Decision

- **The fork's manifests adopt upstream's release ranges.** The merged tree declares no `workspace:^` in any manifest; every DSH dependency reads `workspace:*` and every `vendor/` or `native/` dependency reads `workspace:~`, which is the pair `check-workspace-constraints` accepts. Upstream's own manifests arrive converted, so leaving the fork's 45 on the retired range would fail the gate on files upstream never reads.
- **Upstream's two duplicate-key manifests stay untouched.** `packages/llm/llm-retry/package.json` repeats `@deepseek-ai/dsh-session-projection` and `packages/client/ui-sidebar-documentpreview/package.json` repeats `@deepseek-ai/dsh-office-to-pdf`, both inside `dependencies`, in both parents and at the base commit, with identical values in each pair. JSON last-wins leaves the effective dependency unchanged, and rewriting an upstream-authored manifest inside a merge would put fork content on a file upstream owns and re-conflict at the next sync.
- **Three fork manifests lost their duplicate dependency sections and no entry went with them.** `packages/experimental/webhook` and `packages/session-query/session-query` carried two top-level `dependencies` objects each, where the later object was the effective one; the merged manifests carry one object holding all 3 and all 2 of the fork's entries. `packages/api/remotes` repeated five `devDependencies` keys in both parents, and the merged manifest carries none of them twice while keeping all 34 fork entries and the one upstream added. Each duplicate pair held one value, so the collapse is the file's own effective content rather than a choice between sides.
- **The client assembly keeps `sessionFeedbackRemote`.** The automatic merge dropped the `@deepseek-ai/dsh-command-feedback/remote` import and its entry in the mount list of `packages/api/remotes/src/client/index.ts`, leaving the namespace unmounted with nothing failing at build time. Both are restored, and the five fork Remote contributions in that list — `pluginMarketRemote`, `pluginRegistryProbeRemote`, `messageFeedbackRemote`, `sessionFeedbackRemote`, and `fileUploadsRemote` — mount beside upstream's own.
- **The sensevoice worker spec takes upstream's rewrite, not the fork's synchronization.** Upstream's case drops the call-count poll, awaits `handle.done`, and wraps the body in `try`/`finally`; the fork's added synchronization existed only to survive that poll, so keeping it beside the rewrite would leave a guard for a step that no longer runs.
- **`timeout-guard` applies upstream's newest source under the fork's name.** Upstream changed `packages/guard/timeout-policy` again in this release; the merged `packages/guard/timeout-guard/src/index.ts` differs from upstream's file only in the module doc comment and the registered `name`, 13 lines in total, so upstream's behavior lands without resurrecting the package name the fork's rename retired.
- **Union conflicts keep both parents' additions.** `apps/desktop-host/src/index.ts` (each side added one `node:` import: `fileURLToPath`, `inspect`), `packages/api/gateway/src/index.ts` (upstream's `assertResolvedConfig`/`isPlainObject` value import beside the fork's `dsh-cmdline` type-only import), `packages/extensions/tool-cordis/src/api-catalog.ts` (both catalogs' entries), and `apps/desktop/tests/main-startup.spec.ts` (both suites' imports and cases) resolve as the union rather than a chosen side, because each addition is read by code that survives the merge.
- **The version family aligns inside the merge commit.** The fork's 350 `packages/` manifests, four `apps/` manifests, and the root manifest move to `0.1.7-alpha.2` beside upstream's own, and the fork's single version mirror `SIDEBAR_SERVICE_VERSION` in the since-removed better-sidebar package's `service.ts` moves with them. `pnpm exec tsx scripts/release/verify.ts --family dsh` then resolves the family: 352 members, one version, publish order resolved. `packages/bundle/web-app/package.json` keeps `js-yaml` at `"^4.2.0"`: a registry range for a third-party dependency, which the release-range rule does not cover.
- **The generated catalogs and the bilingual records are regenerated on the resolved tree.** `docs/capability-seams.md`, `docs/config-catalog.md`, `docs/persistence-catalog.{md,zh.md}` with `docs/persistence-schema.json`, and the composition reference of the preset's `cordis-composition-reference` skill (removed with that skill in v0.2.2-rc.2) come from their generators after conflict resolution, and each edited pair re-records its blob hashes through `pnpm run verify-translation-pairing --write`.

## Consequences

The fork ships upstream's v0.1.7-alpha.2 baseline with its patent, document, desktop, better-sidebar, synapse, self-evolve, and plugin-market surfaces intact: 47 manifests exist here and not upstream, 44 of them under `packages/`, and the one upstream manifest this tree does not carry is `packages/guard/timeout-policy`, whose content lives on as `timeout-guard`. Dependency declarations now read identically in both trees, so the fork's own packages join upstream's release tooling instead of standing outside it, and the cost is a sync-time rewrite whenever upstream retires another range. The client assembly's mount list is the one place this merge silently dropped a fork contribution, which is now recorded by the namespace it must carry.

## Alternatives considered

- **Convert only the fork-only manifests and leave upstream's ranges alone.** Not available: upstream's manifests arrive already converted, and the gate reads every manifest in one pass, so a partial conversion fails the same check for the same reason.
- **Deduplicate upstream's two duplicate-key manifests while the merge is open.** Rejected: the repeated keys hold identical values, so the rewrite would change no resolution, while moving fork content onto upstream-owned files re-conflicts at the next sync and hides which side wrote the entry.
- **Keep the fork's synchronization beside upstream's worker-spec rewrite.** Rejected: the call-count poll it synchronized against is what the rewrite deletes, so the retained code would wait on a signal the spec no longer produces.
- **Restore upstream's `timeout-policy` name and retire the fork's rename.** Rejected: the fork recorded the rename, and upstream's source transfers unchanged apart from the name, so taking the name back re-opens a settled decision for no behavior gain.
- **Take upstream's side of the client assembly's mount list.** Rejected: the file's fork additions mount namespaces this tree ships, and the automatic merge had already dropped one of them; the list is the union of both parents by construction.
