# @deepseek-ai/dsh-patent-tools

English | [中文](README.zh.md)

## Summary

Function plugin porting the Sati patent-domain tool set into the DeepSeek Harness. It registers 36 model-facing tools across search, metadata, knowledge queries, claim-chart, office-action parsing, TRIZ contradiction analysis, drafting, analysis reports, evidence judgment, rule checking, figure generation, figure consistency and comparison, the append-only case log, and the workflow/plan state machines. Each tool returns a losslessly JSON-serializable canonical value and exposes a pure `output.render` function that produces the model-facing prose (Sati has no render split; this is the new dsh contract).

`render_patent_document` is owned by `@deepseek-ai/dsh-patent-document` (its `apply()` registers it); this package re-exports `createRenderPatentDocumentTool` and `renderDocumentResult` for library consumers but does not register it, so composing both plugins does not produce a duplicate-name error.

`slop-gate` is a workflow atom, not a model-facing tool: `apply()` registers `slopGateAtom` and `SlopGateHandler` into the global registries because the gate depends on this package's inline slop engine. It runs the deterministic analysis over the state keys named by the stage param `text_keys` (default `['claims_draft']`; the OA response chain passes `['draft_tightened']`), writes `slop_report` + `slop_score`, and — when the text fails the pass line — an evidence-only `slop_revision_hint` (matched phrases with suggested replacements, line-level structure issues; never score numbers, the total, or the pass line). The param `char_budget` declares the length budget: with it the concision dimension is measured against the budget, without it against the paragraph count, which is what the claims chain does. A declared budget also switches the evidence and directness dimensions to the document wording: a body that cites nothing at all is capped below the neutral baseline instead of passing on it, the short-paragraph bonus applies only without a budget, and an opening that still reads as a plea ("请审查员重新考虑…") loses directness even when it names the issue. The `patent_disclosure_v1` manifest's `slop_clean` stage gates the draft and rewinds to `draft_claims`; `patent_oa_response_v1`'s `slop_gate` stage gates the answer body and rewinds to `draft`, in both cases so the rewrite is produced with the hint injected. Library consumers also get `slopGateAtom`, `SlopGateHandler`, `SLOP_GATE_PASS_THRESHOLD`, and the hint builder `buildSlopRevisionHint`. `tighten` is the other half of the same knob: `apply()` registers `tightenAtom` and `TightenHandler` because its verdict needs the same `visibleChars`, now exported from `slop-engine.ts`. That function is also on the package's public surface (`export { visibleChars }`): the `patent-oas` benchmark measures deliverable length with the same counting, and a second copy there would let "the same 4000 characters" mean two different numbers. It counts prose only: table rows and elements and the amended-claims full text are dropped before counting, because those blocks are deliverable carriers rather than text the author may cut. It reads the body (`text_key`, default `draft`), the plan (`plan_key`, default `response-plan`) and `char_budget`, and writes `draft_tightened`, `tighten_report` and `tighten_violations`; a result that grew or is still over budget degrades instead of being written, and a bare body is accepted with the missing itemised list recorded in the report.

Two subprocess budgets stay fixed rather than configurable: the SIGTERM→SIGKILL escalation grace (3 s) because `dsh-patent-data`'s subprocess runner shares it and changing one ends teardown symmetry, and the per-stream output cap (100 000 bytes) because it bounds renderer memory. ## Model Experience

### Tool schemas

#### What the model sees

36 registered tool definitions (see the table above), each with a description, parameter schema, and an `output.render` that renders the canonical result as Markdown prose. Exact descriptions and parameters are in the generated [`patent-tools` schema](../../../docs/tool-catalog.md#deepseek-aidsh-patent-tools). `patent_search` and `patent_metadata` name the channel they read (`Google Patents（nuo 引擎）`) in the rendered result and in any upstream failure, so a search report cites the channel a fact came from instead of inferring it from a hit URL; `patent_search` additionally re-searches through CNIPR when the engine fails or returns no hits (skipping that channel for queries carrying Google field syntax such as `assignee:`), and names the channel that served the call. Both retry a transient upstream failure (timeout, dropped connection) twice under a bounded backoff, and a failure that outlives the retries reports the attempts made. `patent_pdf_download` names the channel per item (`Google Patents（nuo 引擎）` or `CNIPR（中国知识产权网）`) and lists a channel that was consulted without serving in `warnings`, so a fallback is visible rather than folded into the item that another channel produced; its resumed items take the channel recorded in the MANIFEST. `patent_legal_status` names the channel per item, and retries through CNIPR the numbers the engine could not answer, keeping the engine's own reason when that channel has no records either. `matter_log_append` names every defect of a refused round in one message, each with its stable rule id and the fix (the artifact to write first, the fresh path a producing round needs, the version the log never recorded), so a refusal says which part of the archival record is missing rather than only that the round was rejected.

#### Token effect

Fixed definition cost per registered tool on every request; result text is data-dependent and resent only until compaction. No system-prompt section is registered, so there is no additional fixed prompt cost.

#### KV Cache effect

Prefix-stable while the registered tool set and their descriptions are unchanged; changing configuration or the registered set shifts the tool definitions and invalidates reuse from that point.

## Known Limitations and Deferred Work

- **`render_patent_document` ownership** — the tool is registered by `@deepseek-ai/dsh-patent-document`, not here; this package only re-exports its factory.
- **`flexible_plan` name** — Sati's `patentFlexiblePlanTool.ts` declares the name `flexible_plan` (not `patent_flexible_plan`); the dsh tool trusts the Sati name field.
- **Image-modal gate scope** — `analyze_patent_figure` sends the drawing to the resolved figure-model route and is gated on that route's declared image input (denied with error code `model_cannot_accept_image` when absent); the bytes are admitted through the harness attachment store and travel as a durable ref, and an absent store or route fails loud with `setup_required`. `search_patent_figure` reads the index and is intentionally not gated (matches Sati, which gates analyze only). The index is written by `analyze_patent_figure` into Config.figureIndexFile; an absent or empty index returns zero hits with a guidance hint, not an error.
- **Chemistry engine not ported** — `recognize_chemical_structure` and the chemical-characterization check in `validate_specification` degrade to unavailable because the recognition pipeline (VLM two-step analysis, name→SMILES, RDKit validation) is not ported: RDKit is one of its missing pieces, not the only one, so the tool reports the unavailable result whatever the host has installed.
- **Figure primitives** — `figure/mm-primitives` is the single implementation of millimetre coordinate formatting and bounding boxes; the direct-draw renderers, the layout page and the leader-line pass all format SVG numbers through it, so one drawing never mixes precisions across its drawing paths.
- **Vision analysis depth and chemistry engine** — `analyze_patent_figure` ports the Sati wrapper with a single/two-step vision path; the Sati PatentVision/PatentLMM engine's electrical netlist and multi-figure consistency checks are not ported. Figure generation, layout, render checks, the Graphviz/Inkscape/FreeCAD paths, and the keyword figure index are implemented in this package. The chemistry engine (VLM two-step, name→SMILES, RDKit validation) remains unported, so `recognize_chemical_structure` returns an unavailable result and the chemical-characterization check in `validate_specification` degrades with it.
- **Figure generation scope** — `generate_patent_figure` renders SVG through the bundled `@viz-js/viz` WASM engine (Config.figureRenderer); png/pdf and `figureRenderer: 'cli'` go through the `dot` subprocess, which stays a system dependency — those paths fail loud with install guidance when it is missing. That WASM render is synchronous and cannot be interrupted once started, so input size is bounded: raw DOT longer than 64 000 characters (hierarchical/tree engines `dot`/`circo`/`twopi`) or 20 000 (force-directed `neato`/`fdp`/`sfdp`) also switches to the `dot` subprocess, and structured figures are capped at 200 graph elements (nodes + edges, nested nodes included) — rejected with `invalid_tool_input` beyond that, split them into `panels`. `raw_dot` must be self-contained: `image`/`shapefile`/`fontpath` file-reference attributes are rejected, because the subprocess path resolves them against the host filesystem. Leader-line numerals are on by default for block-diagram/component-hierarchy SVG (off for flowchart and `raw_dot`/`template`; per-call `leader_lines` overrides): numerals sit outside the component with a `<line>` connector instead of the embedded label suffix; non-SVG formats keep embedded numerals and return a warning. Placement converts node coordinates through the enclosing group's translation, skips positions that would cross a drawn edge, arrowhead, or edge label, and expands the root `viewBox`/`width`/`height` when a numeral or leader would fall outside the declared canvas — SVG content outside the canvas is not rendered. A node inside a scaled, rotated, or flipped group cannot be positioned this way: its numeral is embedded in the component label with a warning. After every generation the tool reports drawing-wording warnings derived from the Implementing Regulations of the Patent Law Article 21 and the CNIPA Guidelines Part I Chapter 1 §4.3: unnecessary annotations (annotation prefixes, text references, dimension callouts, scale callouts, sentence-ending punctuation), non-Chinese words (acronyms and numeric/symbol tokens excepted), a figure number drawn inside the figure, a numeral bound to brackets or quotes, and non-Arabic-numeral references; the check only reports and never rewrites the input. The vector figure types (`circuit`/`plot`/`cross_section`/`sequence_diagram`/`appearance_view`) bypass Graphviz and go through `vector-figure-build`, which emits millimetre-coordinate SVG fragments: circuit symbols placed on a grid with orthogonal wiring and filled junction dots, plots with axes, ticks and no scale annotation, cross-sections with 45° hatching (opposite direction or different spacing for adjacent parts) and cutting-plane marks — a part that omits `hatch` silently takes the default 45°/3 mm, so the tool reports that default per figure, and a part that is not a cut solid declares `hatch: "none"` instead of being faked with thin polygons, sequence diagrams with lifelines and message arrows, and appearance-design sheets that arrange the six orthographic views in first- or third-angle order at one shared scale with each view name below its own view. `panels` renders multi-figure sets (`fig1A`/`fig1B`, …) with one shared numeral series; panel suffixes must be unique and `panels` cannot be combined with a top-level structural or vector input (both are rejected instead of overwriting a file or dropping a figure); appearance-view fragments must be geometry only — script, style, foreignObject/iframe/object/embed, animation, event-handler attributes, `javascript:` URLs, and ENTITY/CDATA are rejected before layout; a per-call `figure_family` continues numerals across generations for components recorded under the same family in the figure index — no family declared means independent per-figure numbering, and index entries without `figureFamily` never participate. `semantic` color fills are allowed only when color carries technical content per CNIPA Guidelines Part I Chapter 1 §4.3 (2023 rev., `grayscale` is the default); `raw_dot`/`template` outputs carry no structured components or connections (search-index entries remain partial). Every delivered SVG is render-checked after layout and before text-to-path, including plain SVG output (previously only the png/pdf SVG chain and vector direct draws were checked); net clearance is per figure type (`RENDER_CLEARANCE_MM`): 1.5 mm for cross-sections, structure line art and embedded-numeral Graphviz figures, 0.5 mm for leader-line/raw-DOT figures, 0.7/0.9/0.7 mm for circuit/plot/sequence diagrams, and off for appearance-view fragments. Text and segments in the same `<g class="node|edge">` group — a node label inside its node, an edge label beside its own edge — are exempt from the clearance and crossing checks: that is layout, not a cross-element collision.
- **Drawing submission profiles and page layout** — `figure/office-profile` fixes the verified per-office values: China A4 with 25/25/15/15 mm margins, the `图N` figure number (only from two figures up, per Guidelines Part I Chapter 1 §4.3) and drawing-sheet page numbers written `第N页 共M页` (`第N页` for a single sheet); PCT's usable drawing area and 0.32 cm minimum character height (Rule 11.6(c), 11.13(h)), `Fig. N` numbering, no colour (11.13(a)) and `1/3` sheet numbers; the USPTO margins and minimum character height (37 CFR 1.84(g), 1.84(p)(3)) with `FIG. N` numbering. Given `target_office`, `figure/submission-page` lays the drawing out on a fixed-size sheet (figure number below the drawing, sheet number at the bottom of the type area) and `figure/compliance` then checks the colour policy (PCT rejects colour outright; a US utility application needs a petition), unnumbered multi-figure sets, and the laid-out character height, returning the layout scale and sizes. Layout reaches png/pdf through the SVG chain: Graphviz's `page`/`size`/`margin` attributes only affect the drawing's own canvas (measured locally on Graphviz 15.1.1 — `page` produces no sheet for svg/png/pdf, `size` only scales down when exceeded, `margin` only adds whitespace), so a png/pdf call that asks for `target_office` renders SVG first, lays it out, checks it, and exports it with Inkscape; without Inkscape it falls back to the renderer's direct output and reports that layout and the render check did not apply. A png/pdf call without `target_office` on a Graphviz figure is unchanged. EPO is not in the profile table: EPC Rule 46/47 and the EPO Guidelines were unreachable during research (epo.org returns 403). The two-thirds readability rule only reports the measured reduced character height without a threshold warning, because none of the three offices states a numeric floor for that case.
- **Two-step analysis degradation** — with `figureAnalysisMode: 'two-step'`, an unparseable structure-extraction pass returns a best-effort result with empty components plus a warning and skips the description pass; the image gate and result shape are identical to `single`.
- **Structure figure scope** — `generate_structure_figure` requires host FreeCAD 1.1+ (`freecadcmd`) and stays off until `structureFigureEnabled: true`; a closed gate or a missing executable fails loud with `setup_required` and install guidance, never a silent schematic fallback. Each requested view becomes one `TechDraw::DrawViewPart` (not `DrawProjGroup.addProjection`, which throws in FreeCAD 1.1) rendered through `TechDraw.viewPartAsSvg` — the geometry fragment carries no template border, title block, or figure number, meeting the line requirements of CNIPA Guidelines Part I Chapter 1 §4.3; for two or more figures the `图N` number is written below the drawing by the `target_office` layout step, as that section requires the number to sit directly below its drawing — wrapped into a standalone black-stroke SVG. Callout numerals are anchored in the Python script via `DrawViewPart.projectPoint`, sharing the fragment coordinate frame, and are offset outward with a leader line. The subprocess HOME/temp/cache directories are redirected into the output directory (best-effort; macOS FreeCAD resolves its cache from `~/Library/Caches/FreeCAD` regardless of HOME), and the script pins the document `TransientDir` to an output-directory subdirectory, because TechDraw copies the page template relative to that property — a sandbox that denies the FreeCAD cache directory leaves it empty and resolves the copy to `/`, failing the render. The subprocess temp variables (`TMPDIR`/`TEMP`/`TMP`) must name an existing directory: pointed at an absent path, `freecadcmd` 1.1.3 dies with SIGSEGV before running any script, printing nothing on stdout or stderr and reporting no exit code, so the renderer creates that directory inside the output directory before spawning — a render that fails with no artifact and no diagnostics means checking it first; `HOME` and `XDG_CACHE_HOME` at absent paths only add cache warnings (measured). Success is judged solely by exit code plus manifest presence because `freecadcmd` treats preference/cache write failures as non-fatal warnings. Output SVGs pass the same `assertSafeSvg` gate as the Graphviz path, and results persist to the figure index with `figureType: 'structure'`. With `target_office` every view SVG is laid out on that office's A4 sheet and the laid-out sizes are returned; without an explicit `caption` no figure number is drawn, because how a model's several views end up numbered is the caller's decision over the whole application's figure order. A directory `model_path` renders one figure per supported model (sorted, incrementing figure numbers) but is rejected with `invalid_tool_input` when `callouts` are supplied, since a callout's 3D anchor is model-specific. Passing `model_paths` instead projects several model files into one figure — one `Part::Feature` per file, all attached to the same view's `Source`, so TechDraw resolves occlusion between the parts in one hidden-line pass — which is how an assembly is drawn; there every callout must name its owning part through `callouts[].model` (a 0-based index into `model_paths`), and the script checks the anchor against that part's real geometry, failing the render before any projection when the point lies more than 0.5 mm away; `scale` must be a finite positive number and `figure_number` a positive integer, both validated before any render. `details` adds a partial enlargement: each entry names a base view plus a window in **model** coordinates (`center` `[x,y,z]`, `radius_mm`) and a magnification, and the script builds one `TechDraw::DrawViewDetail` off that base view, leaving the clipping to the circle and the magnification to TechDraw (measured: a detail fragment's coordinates scale with `DrawViewDetail.Scale`, unlike a `DrawViewPart` fragment, which stays in model millimetres; the boundary circle TechDraw draws is 1 % wider than the clip circle, so the canvas is sized from that slack). The window centre is the base view's `projectPoint(centre) − C`, where `C` is the tight projected-geometry centre the callout anchors already use — passing the raw `projectPoint` value centres the window somewhere else. The base view gets the window circle and its `reference` label drawn by the script, because `ShowHighlight` only feeds the GUI page: `viewPartAsSvg` of the base view is byte-identical with and without the detail view. `base` must be one of `views`, `radius_mm` and `scale` must be finite and positive, and a directory `model_path` rejects `details` for the same reason it rejects `callouts` (the window is model-specific). Each view SVG is render-checked after layout and before text-to-path; a callout leader now stops at its numeral's bounding-box edge (same glyph ratios the checker uses) and carries `data-dsh-role="leader"`, so a leader no longer runs through its own numeral. Dimension annotation and a DXF export path remain unimplemented.
- **CAD section source scope** — `sections.source` cuts a cross-section out of a CAD model on a plane instead of taking handwritten coordinates, over the same host FreeCAD channel as `generate_structure_figure` (Config.freecadExecutable / freecadRenderTimeoutMs) but with no separate gate: the input field is the opt-in, and a host without the `subprocess` service or `freecadcmd` fails loud with `setup_required` rather than falling back to a schematic. Every material region of the slice becomes one `parts` entry, claimed by an `anchor` point inside it, and the region inventory (count, net area, drawing extent) is returned as a warning so the caller can place labels: region order is OCCT's edge order, so matching by index would hang a label or a hatch group on the wrong region, and a count mismatch, an anchor outside all material, an anchor inside a hole, or two parts claiming one region are each `invalid_tool_input`. Hatching comes from `TechDraw.makeGeomHatch` in the view frame with the scaled contour fed straight in, so a hole edge is clipped exactly where the drawing clips it — the polygon-wise clip in `figure/section-diagram` cannot do that, and a part with holes is rejected unless the caller supplies pre-cut `hatchSegments`. Four measured `makeGeomHatch` constraints govern the path: the face must lie in the z=0 XY plane (a translated or x-tilted face returns an empty `Compound` with 0 edges, not `None`); hatching must be produced in the view frame, because a model-frame hatch mirrors the angle in the drawing; `patFile` must be passed explicitly, since `makeGeomHatch(face, scale)` dies with SIGSEGV (exit 139) and loses the block-buffered stdout; and an unknown pattern name or an unreadable `.pat` returns `None` without raising, so the script turns every one of these into a hard failure instead of a drawing that has an outline and no hatching. The `.pat` is written with `delta = 1`, so `patScale` equals the millimetre spacing exactly (measured across 0.25/0.5/1/2/3.5/10 mm) and the `.pat` angle is the drawing-frame angle. `source.scale` multiplies the cut coordinates before hatching, so `parts[].hatch.spacing_mm` stays drawing-millimetre spacing while `labels`/`centerlines`/`cutting_marks` must use the same scaled coordinates. `part_size_mm`, when given, is compared with the model bounding box (order-independent, 0.1 % relative) and a mismatch is rejected, because STEP declares its unit in the file header while IGES/BREP carry none and a wrong unit scales the whole drawing — omitting the declaration leaves that unchecked.
- **Matter-log archival is gated per session, not per round** — the patent preset's delivery gate requires a successful `matter_log_append` before `render_patent_document` or `build_patent_filing` may run, and the ledger behind it records tool names that returned without error, without a `blocked: true` result, and without a downstream post-execute block, per agent for the session. One archival entry therefore clears every later gated delivery in that session: the floor is "the session archived its case before shipping", not "every render carries its own entry". Per-round counting would need a turn-scoped ledger, which would tighten the `rule_check` / `law_verify` prerequisites too.
- **Knowledge note / PDF download wiring** — `knowledge_note_save` writes files under Config.noteDir (a native knowledge.db write API is deferred), and `patent_pdf_download` resolves its batch runner per call over a late-bound `ctx.get('patentData')` lookup (`createDownloadChannelRunner`): China publication numbers first go to the CNIPR channel (`ctx.patentData.createCniprChannel()`, nothing while the deployment leaves `cniprEnabled` off) for their full-text link, a channel that cannot serve them is reported in `warnings` and hands them to the Google Patents leg, a present service drives the unified ego stack (via `ctx.patentData.createEgoSession()`), and an absent service or an unusable browser falls through to a browser-free scrape of each page's CDN link, which the tool's own fetch fallback downloads with bounded retry/backoff (timeout, retry, and Retry-After-aware wait). `patent_legal_status` reads the same service per call through a late-bound lookup and retries unanswered numbers through CNIPR. The lookup is per call because `patent-data` declares `inject: ['subprocess']` and therefore activates after this package's apply; see [the service-resolution Agent Note](../../../.agents/notes/implemented/bug-fix/2026-09-21-patent-pdf-download-resolves-service-per-call.md). browseros-neo, playwright, and browser-use participate in probing but never in downloads.
- **Retrieval quality is not scored by `patent_eval`** — its `retrieval` mode counts the terms a query names (three or more scores 1.0, one or two 0.5) under the dimension `关键词条数`, and never reads a result list, so that score describes the query's form rather than how well a search ranked the right document. Result ranking is measured instead by `rankOfFirstRelevant`, `meanReciprocalRank`, and `ndcgAtK` (`src/eval/ir-metrics.ts`) against the repository-authored corpus, relevance judgments, and recorded FTS5 BM25 baseline under `tests/fixtures/retrieval-corpus/`. Corpus and baseline are both in-repo and small, so the numbers locate the current baseline and gate regressions in the metric code; they are not a statement about retrieval quality in general, because no third-party dataset is used and nothing here calibrates against human relevance judgments at scale.
- **Semantic recall removed** — `patent_case_search` keeps FTS/LIKE only; the embedding-based semantic recall path is not ported (dsh ships no vector infrastructure yet).
- **Evidence rule assets** — `evaluate_evidence` resolves `evidence-rules.yaml` through `@deepseek-ai/dsh-patent-rule`'s asset location; without it the engine falls back to default weights.
- **TRIZ analysis is inventor-side and narrow by design** — `triz_contradiction_analysis` reads one disclosure at a time: it builds no problem dependency graph, measures no hallucination rate, and merges nothing across documents. Its contradictions are design-level trade-offs between engineering parameters, so they never enter an office-action or invalidity argument — the three-step step-2 problem statement stays with `checkAtomic` and the inventiveness subgraph. A contradiction whose evidence does not locate in the disclosure text is dropped and counted instead of reported, and a matrix cell carrying no recommendation is reported as a gap rather than filled from a neighbouring cell.

- **`claim_lint` reads claim form, not substance** — the antecedent-basis rule splits the term after 「所述」 at function words and caps it at eight characters; Chinese has no morphological boundary, so a composite term that is not introduced as a whole (「所述转子铁芯外圆」 where 「转子铁芯」 is introduced) is reported at warning level instead of error. The wording rules (functional/effect limitation, process feature, non-technical content, commercial language, references to the description or drawings) are vocabulary matches: a hit means the drafting needs a human read, not that the claim is defective. The tool does not compare claims against the description (that is the feature-coverage check in `validate_specification`) and does not judge patentability.
- **Violation locators cover literal hits only** — `rule_check` and `validate_specification` report `line` and `matchedSentence` for the earliest hit counted into the violation, so a warning can be judged where it occurs instead of by re-reading the whole document. For keyword checks that exempt negated or quoted mentions (`negationContext`, `quoteImmune`), that is the earliest hit left after the exemptions, not the earliest occurrence of the word in the text. Checks that report an absence or an aggregate (missing sections, coverage rates, numeric-range endpoints), `quote_repetition` (its evidence carries the repetition count, so it is no run of the text), and checks reading a separate input field (title, abstract, claims) carry neither, because a line into the specification would point at nothing.

- **A `rule_check` with block-level violations is not delivery evidence** — its result carries `blocked: true` when any violation has `action: block`, and the patent rule plugin's delivery ledger ignores a prerequisite whose result declares that flag. A run that found a blocker therefore has to be fixed and re-run; a run that only found `review` hits still counts, because the delivery output gate asks for approval on the rendered artifact. The `blocked` flag covers the self-check's own verdict; it does not yet prove the checked text matches the deliverable.
- **Blank text is an input error** — `rule_check` rejects a `text` that is empty or whitespace-only with `invalid_tool_input`, so a zero-byte call cannot leave a successful prerequisite record. The patent preset also requires the result's `evaluated` list to be non-empty before a delivery render or filing, which keeps the identity of the text the run actually read.

- **Reported results carry the identity of what they evaluated** — `rule_check` and `validate_specification` take their text inline, so two callers checking "the same document" can hand over different revisions of it. Measured on a real case, three teammates re-running one gate passed 12164, 12166 and 12177 characters, none of them the 13399-character file on disk, and the verdicts differed exactly where the texts did. Each result therefore ends with an `评估输入` line giving the character count and digest of every text field it read, so comparing two runs is mechanical. That line only *reports* divergence: nothing yet forces a run to match the artifact on disk, and the delivery gate checks that at least one text was evaluated rather than comparing the digest with the render arguments.

- **Specification checks separate form defects from substantive conclusions** — `validate_specification` returns `not_assessed` for what deterministic rules cannot decide (enablement under A26.3, claim breadth under A26.4, drawing legibility and scale, photo suitability, a missing figure analysis, or a missing abstract-figure designation), and `passed` means only that the rules it ran found no error. `spec-check` writes per-family verdicts (`spec_form_check_passed`, `spec_claims_check_passed`, `spec_figure_check_passed`, `spec_prohibitions_check_passed`) plus `spec_not_assessed`; `legal-gaps` maps the form and claim verdicts to their provisions and keeps enablement unassessed until an `enablement_report` exists. A placeholder draft, a claim citation, commercial advertising, a utility model without drawings, or a figure-number gap therefore blocks the default workflow instead of passing.
- **`adversary-review` is a deterministic heuristic gate, not a model review** — it reads `draft_tightened`/`draft`, `claims`, `office_action`, and `reference_documents` (or, when that key is empty, citations from `oa-parse`). Evidence gaps carry a statute derived from the gap kind and the notice's rejection types instead of defaulting every gap to A22.3; keyword misses use a lower heuristic confidence. It writes `adversary_review_passed` (false only when argument strength is `insufficient`), and the `oa-response` `legal-gaps` profile records a failure as severity `warn` so the run stays deliverable while the gap remains visible in the summary.
- **Later checks cover artifact-level gaps the form rules cannot see** — the abstract figure is read from the request-form field (`abstract_figure_number`), never inferred from a phrase inside the abstract; `draft_specification` emits a deterministic ≤300-character abstract with a keyword line, so the default workflow can feed `spec-check` without a separate abstract call. Background citations (jurisdiction, number, date), effect-to-prior-art comparison, sequence-listing references, images and tables in the text, term/mark consistency, and utility-model drawing content are warnings. `verify_patent_figure` with `delivery_review=true` adds photos (`<image>`), a full-sheet frame, landscape orientation, and non-essential figure words to its findings.
- **Specification style checks key off shapes a markdown text can show** — the required-section set follows the patent type and whether the application has drawings: an invention without drawings needs four parts, a utility model always needs 附图说明, and a present-but-empty drawing section is an error. The heading-set check allows the required part headings plus the `说明书` wrapper heading `render_patent_document` writes, and reports every other heading as extra, so a deployment whose template titles its wrapper differently sees that title reported. The parenthesized-figure-mark check reads `名称（数字）` and `名称(数字)` and skips a name ending in an enumeration suffix (`实施例（1）`, `图（2）`), so an enumerated reference that happens to label a part is not reported. Paragraph numbering is a warning, not an error: no law or guideline clause requires or forbids it, and whether a filing uses it is a property of the delivery format.

- **`patent_workflow_run` background runs** — `run_in_background: true` registers the manifest run with `ctx.jobs` (`@deepseek-ai/dsh-jobs` plus `@deepseek-ai/dsh-tool-jobs`) and returns the job id at once; the settled job carries the same rendered text a foreground call returns, collected through `job_output`. Without a background-task service the flag fails loud with `setup_required` instead of silently blocking the turn, and it is rejected with `invalid_tool_input` on the graph path. A case run writes one deterministic artifact path per case and manifest, so a second live run for the same pair is refused with `file_conflict` rather than letting the two overwrite each other's record; a run without a case writes no artifacts and is not constrained. Each stage advance sets the job's progress line (`3/10 extraction`), which `job_list` shows while the run proceeds. The job owns its own abort signal, because the run outlives the call that started it: `job_kill` or owner teardown cancels it, and stage boundaries are where an abort takes effect (an in-flight model call is not interrupted).
