## 逐条说明

### P-SPC-04 超时：已恢复

首次调用按注入返回 `tool_timeout`，没有起引擎。恢复调用把 `outputName` 改为 `pilot-filing-retry`，重新走真实 Python 引擎：`docxPath` 存在，`verification.passed` 为 `true`，分节是 `abstract`、`claims`、`specification`，文本没有声称已提交 CNIPA。题面的四条判定成立。

本轮在调用返回后检查了子进程表（为空）与 `TMPDIR`（没有 `dsh-patent-filing-*` 目录）；引擎的临时工作目录被 `finally` 删除。输出目录里保留两份 docx：干净场景的 `pilot-filing.docx` 与恢复的 `pilot-filing-retry.docx`，都是题面要求的成品，不是临时残留。

### P-SPC-02 空结果：已恢复，并暴露假闭环风险

首次调用成功，但 `passed=true`、没有 sections 错误、`evaluated` 为空。题面要求 `passed=false` 且 sections 错误存在，外部判定不成立；只看工具的成功状态会把它写成「校验通过」，这是假闭环。

恢复调用增加 `patent_type: 'invention'`，`passed` 变为 `false`，sections 错误仍是「缺少必要章节：背景技术、发明内容、具体实施方式」，`evaluated` 有 `text` 的 20 字与 `sha256:cc2a67…` 指纹；同时 `patent_type_assumed` 的 warning 消失。外部判定成立。

### P-SPC-01 取消：已恢复

首次调用按注入返回 `tool_aborted`。恢复调用增加 `claims: '1. 一种检测装置，包括壳体。'`，返回 `complete=true`、`missing_inputs` 为空、五部分顺序正确、摘要 72 字、实施例块 1 个、丢弃 0 个。题面的六条判定成立。多给的 `claims` 触发了 33 条替代索引的评估，但不改变本轮的完整度判定。

### 假恢复与重复检查

三次注入都没有原样重放失败调用；每次只有 1 次恢复调用，低于 2 次上限。空结果首次调用是「成功」形状，脚本没有把它的成功当闭环；恢复后的外部判定由题面字段逐条核验。

## 族内结论

本族 3 种注入全部覆盖，3/3 已恢复；1 次空结果注入属于「成功但外部判定不成立」。没有同名同参数重复、没有超过 2 次的重试、没有假恢复。

本族是四族里唯一有真实子进程与文件输出的：子进程 0、引擎临时目录 0、成品按题面保留。P-SPC-03 的题面 draft 缺槽位问题在干净场景日记录，不通过注入掩盖；它在注入轮没有可恢复的题面参数，因此不作为注入样本。
